## ① O-14 · ABC as a contract

**Anchor:** *"An ABC is a promise the compiler enforces."*

Last session's duck typing works — until it doesn't:

```python
class BrokenSplitter:
    def splitt(self, amount, users):    # typo. Nothing complains.
        ...

group = Group(BrokenSplitter())         # accepted happily
group.add_expense(...)                  # 💥 AttributeError, 200 lines later
```

The failure lands **far from the mistake**. Worse, in an interview you can't point at anything that says what a splitter must provide.

### The fix — write the promise down

```python
from abc import ABC, abstractmethod

class SplitStrategy(ABC):
    """Any splitter must be able to divide an amount between users."""

    @abstractmethod
    def split(self, amount: float, users: list[User]) -> dict[str, float]:
        ...

    def describe(self) -> str:          # concrete methods are allowed too
        return self.__class__.__name__
```

```python
class EqualSplit(SplitStrategy):
    def split(self, amount, users):
        share = round(amount / len(users), 2)
        return {u.user_id: share for u in users}

class Broken(SplitStrategy):
    def splitt(self, amount, users):    # typo again
        ...

>>> SplitStrategy()     # TypeError: Can't instantiate abstract class
>>> Broken()            # TypeError: ...with abstract method split
>>> EqualSplit()        # fine ✅
```

**The error now arrives at object creation** — right next to the mistake, not two hundred lines away.

```
   ┌────────────────────────┐
   │   SplitStrategy (ABC)  │   "everyone here CAN split()"
   │   @abstractmethod      │   — cannot be created directly
   │   split()              │
   └───────────┬────────────┘
       ┌───────┼───────┐
       ▼       ▼       ▼
   Equal    Exact   Percent      each MUST implement split()
```

### What an ABC buys you

| | Duck typing | ABC |
|---|---|---|
| Works? | Yes | Yes |
| Error timing | at call, far away | at creation, immediately |
| Documents the contract | no | **yes — it's the file** |
| Interviewer can see the design | not really | **at a glance** |

### The honest limit

An ABC checks that the **method exists**. It does not check that your implementation is correct or sane. It's a contract about *shape*, not about *behaviour* — that part is Liskov's job, on L10.

### Python vs Java, the interview question

> *"Does Python have interfaces?"*
>
> *"Not as a keyword. The equivalent is an abstract base class with `@abstractmethod` — or plain duck typing, since Python checks at call time. ABCs are what you use when you want the contract enforced and documented."*

That answer is correct, complete, and unmistakably Python.

## 🔨 Build it — 25 min

### 🔨 1 — SplitStrategy for real

```python
# In lld/splitwise/, create the ABC SplitStrategy with:
#     @abstractmethod split(self, amount, users) -> dict[str, float]
#     @abstractmethod validate(self, amount, users) -> bool
#     concrete: name(self) -> str  →  returns class name
#
# Implement:  EqualSplit, ExactSplit(amounts: dict), PercentSplit(percents: dict)
#
# validate() rules:
#     EqualSplit   → always True
#     ExactSplit   → the amounts must sum to the total
#     PercentSplit → the percents must sum to 100
```

**Acceptance:** all three are creatable; `SplitStrategy()` raises; an `ExactSplit` whose amounts don't add up returns `False` from `validate()`.

### 🔨 2 — use it polymorphically

```python
# strategies = [EqualSplit(), ExactSplit({...}), PercentSplit({...})]
# for s in strategies:
#     print(s.name(), s.validate(1000, users), s.split(1000, users))
#
# One loop. No if-chain. Three different behaviours.
```

**Acceptance:** the loop is three lines and mentions no class name.

### 🔨 3 — the interview question, written down

> In a docstring at the top of the file, answer in 3 sentences:
> **"Why use an ABC here instead of just duck typing?"**

Write it out properly. You will be asked this, and a written answer you composed yourself is retrievable in a way a read one isn't.
