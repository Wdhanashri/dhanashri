## ① O-21 · The 6-step method

**Anchor:** *"Clarify → nouns → verbs → relationships → code → extend."*

```
┌────────────────────────────────────────────────────────────┐
│ 1. CLARIFY    3 questions. Scope, scale, edge cases.  3min │
│ 2. NOUNS      List the entities.                      3min │
│ 3. VERBS      What can each do? → methods.            3min │
│ 4. RELATE     has-a? is-a? Draw the boxes.            5min │
│ 5. CODE       Core flow first. Working > complete.   25min │
│ 6. EXTEND     "What if we needed X?"                  5min │
└────────────────────────────────────────────────────────────┘
```

**The trap: starting at step 5.** Under pressure everyone wants to type immediately. Steps 1–4 take twelve minutes and are where most of the marks are — an interviewer is watching *how you think*, and steps 1–4 are the only place that's visible.

### Step 1 — the three questions

Always ask. Silence here reads as "doesn't gather requirements."

```
Scope:  "Multiple floors, or one level?"
Scale:  "Roughly how many spots? Does that change the design?"
Edges:  "What happens if the lot is full? Do we handle payment?"
```

Then **state your assumptions out loud** and move: *"I'll assume one lot, multiple floors, three vehicle sizes, and hourly pricing. Shout if you'd rather I do something else."*

### Step 5 — the priority order

```
1. the happy path, working end to end
2. one extension point where change is likely
3. edge cases, if time remains
```

**A working small design beats a half-finished grand one.** Every time.

### Step 6 — pre-empt the follow-up

Before they ask, say: *"If we needed weekend pricing, I'd add a `WeekendPricing` strategy — no existing class changes."* You've just answered the next question and demonstrated OCP without saying "OCP."

**Recall prompt:** *Name the 6 steps in order.*

## ② Parking Lot — walk it with me

**This is the "Hello World" of LLD.** If you know one design cold, make it this one.

### Step 1 · Clarify

```
Q: Multiple floors?              A: yes, assume 3
Q: Vehicle types?                A: motorcycle, car, bus
Q: Pricing?                      A: hourly, but may change
Q: What if full?                 A: reject with a clear message
Q: Payment?                      A: keep it simple — calculate the fee, don't process it
```

### Step 2 · Nouns

```
ParkingLot · ParkingFloor · ParkingSpot · Vehicle · Ticket · PricingStrategy · DisplayBoard
```

Not `Time`, not `Fee` — those are values, not objects. **(L2's rule: a noun earns a class when it has data *and* behaviour.)**

### Step 3 · Verbs

```
ParkingLot   → park(vehicle), unpark(ticket), is_full()
ParkingFloor → find_free_spot(size), free_spot(id)
ParkingSpot  → assign(vehicle), release(), is_free()
Ticket       → duration()
Pricing      → calculate(hours, size)
```

### Step 4 · Relate

```
     ┌──────────────┐
     │  ParkingLot  │ ── has-a ──→ list[ParkingFloor]
     │              │ ── has-a ──→ PricingStrategy      ← swappable
     └──────────────┘
            │
     ┌──────▼───────┐
     │ ParkingFloor │ ── has-a ──→ list[ParkingSpot]
     └──────────────┘
            │
     ┌──────▼───────┐
     │ ParkingSpot  │ ── has-a ──→ Vehicle | None
     └──────────────┘

     ┌──────────────┐
     │   Vehicle    │  ← is-a ──  Motorcycle · Car · Bus
     └──────────────┘
```

**Everything is has-a except `Vehicle`.** That's normal, and it's what L5 predicted: composition is the default, inheritance is the exception.

### The design decisions, stated

| Decision | Why |
|---|---|
| `PricingStrategy` is injected | pricing changes often — the obvious extension point |
| `Vehicle` uses inheritance | Car IS A Vehicle, adds nothing removed → passes both tests |
| `Ticket` is its own class | issue time + spot + vehicle always travel together → **O-04** |
| `ParkingSpot` holds a `VehicleSize` | a bus can't use a motorcycle spot |
| No Factory (yet) | only three vehicle types, created in one place — **it would be indirection with no payoff** |

**That last row is deliberate.** Say it out loud in the interview. Restraint scores.

## 🔨 Build it — 55 min

Create `lld/parking_lot.py`. **Follow the steps in order — do not skip to code.**

### 🔨 Step A — on paper, 8 min, no keyboard

> Write nouns, verbs, and draw the boxes yourself before looking at mine again. Then compare. Differences are interesting, not wrong.

### 🔨 Step B — the skeleton, 15 min

```python
# Enums:      VehicleSize(MOTORCYCLE, CAR, BUS), SpotStatus(FREE, OCCUPIED)
#
# class Vehicle(ABC):        plate, size property (abstract)
#   Motorcycle / Car / Bus subclasses
#
# @dataclass ParkingSpot:    spot_id, size, vehicle=None
#     is_free(), can_fit(vehicle), assign(vehicle), release()
#
# class ParkingFloor:        floor_no, spots: list[ParkingSpot]
#     find_free_spot(size) -> ParkingSpot | None
#
# @dataclass Ticket:         ticket_id, vehicle, spot, entry_time
#     duration_hours() -> float
```

**Acceptance:** you can create a floor with 10 spots and find a free one for a car.

### 🔨 Step C — pricing as a Strategy, 10 min

```python
# class PricingStrategy(ABC):
#     @abstractmethod calculate(hours: float, size: VehicleSize) -> float
#
# HourlyPricing   → rate per hour, by size
# FlatRatePricing → one price regardless of duration
#
# Do NOT put an if-chain on pricing type anywhere.
```

**Acceptance:** two pricing objects give different fees for the same ticket, and `ParkingLot` was not edited between them.

### 🔨 Step D — ParkingLot, 15 min

```python
# class ParkingLot:
#     __init__(self, floors: list[ParkingFloor], pricing: PricingStrategy)
#         ← injected. Both of them.
#     park(vehicle) -> Ticket        raise ParkingFullError if nothing fits
#     unpark(ticket) -> float        frees the spot, returns the fee
#     availability() -> dict         free spots per size
#
# Custom exception: class ParkingFullError(Exception)
```

**Acceptance:** a full demo runs — park 3 vehicles, print availability, unpark one with a fee, park again into the freed spot.

### 🔨 Step E — step 6, in writing, 7 min

> At the bottom of the file, answer three "what if" questions in comments — **code not required, design answer required**:
>
> 1. *"What if we add electric-vehicle spots with charging?"*
> 2. *"What if pricing differs on weekends?"*
> 3. *"What if we need a display board showing free spots per floor?"*

<details>
<summary>Check your answers</summary>

1. New `VehicleSize.EV` + new spot type. If charging has behaviour, `ChargingSpot(ParkingSpot)` — but check the is-a test first.
2. New `WeekendPricing(PricingStrategy)`. **Nothing else changes.** That's OCP, and it's why pricing was a strategy from the start.
3. **Observer.** `ParkingLot` is the Subject; `DisplayBoard` subscribes and updates on park/unpark. The lot never learns the board's name.

If you got the third one, L12 landed.
</details>
