## ① O-07 · Invariants — the real reason

**Anchor:** *"A class protects a promise, not a variable."*
**Yaad rakho:** *"Bahar se button, andar se machine."*

The textbook answer is *"encapsulation means hiding data using private variables and providing getters and setters."* That answer is **why so much OOP code is garbage** — it produces classes that are just dicts with 20 extra lines.

Here is the real reason.

### An invariant is a promise your class always keeps

```python
class BankAccount:
    def __init__(self, balance):
        self.balance = balance          # public

acc = BankAccount(1000)
acc.balance = -50000                    # nothing stopped this
acc.balance = "hello"                   # or this
```

The promise *"a balance is a number and never below zero"* has no way to be kept. Anyone can break it from anywhere, and when you find the corruption you have **no idea which line did it**.

```python
class BankAccount:
    def __init__(self, balance: float):
        if balance < 0:
            raise ValueError("balance cannot be negative")
        self._balance = balance         # _ = internal

    def withdraw(self, amount: float) -> None:
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount
```

Now the promise is kept in **exactly two places**, and there's no third way in.

### The test

> **Ask: is there a rule about this data that must always be true?**
>
> Yes → make it internal, and expose methods that respect the rule.
> No  → leave it public. Seriously.

A `Point` with `x` and `y`? No rule. Leave them public. Don't write `get_x()`.

### Python is honest about privacy

| Written | Means | Enforced? |
|---|---|---|
| `balance` | public | — |
| `_balance` | "internal — don't touch" | **No.** Convention only. |
| `__balance` | mangled to `_Class__balance` | Makes accidents unlikely, not impossible |

**Python has no true private.** If asked in an interview, say exactly that — *"Python enforces it by convention, not by the compiler"* — and you'll sound like someone who writes Python rather than someone reciting Java.

**Recall prompt:** *What's the one question that tells you whether a field should be private?*

## ② O-08 · `@property`

**Anchor:** *"`@property` — looks like data, runs like a method."*

Java forces `getBalance()`. Python doesn't, and shouldn't.

```python
class User:
    def __init__(self, first: str, last: str):
        self.first = first
        self.last = last

    @property
    def full_name(self) -> str:            # computed, not stored
        return f"{self.first} {self.last}"

>>> u = User("Dhanashri", "W")
>>> u.full_name          # NO parentheses — reads like an attribute
'Dhanashri W'
```

### Why this matters more than it looks

You can start with a plain attribute and **upgrade it later without breaking anyone's code**:

```python
# version 1
class Circle:
    def __init__(self, radius):
        self.radius = radius
        self.area = 3.14159 * radius ** 2      # ❌ goes stale if radius changes

# version 2 — same usage, now always correct
class Circle:
    def __init__(self, radius):
        self.radius = radius

    @property
    def area(self):
        return 3.14159 * self.radius ** 2      # computed on demand

>>> c.area      # unchanged for every caller
```

**That's the Python argument against writing getters up front.** In Java you write them defensively because you can't change your mind later. In Python you *can*, so don't pay the cost until you need it.

### Setters, when you need validation

```python
    @property
    def balance(self) -> float:
        return self._balance

    @balance.setter
    def balance(self, value: float) -> None:
        if value < 0:
            raise ValueError("negative balance")
        self._balance = value

>>> acc.balance = -5      # ValueError — assignment itself is guarded
```

**Gotcha:** inside `__init__`, `self.balance = x` will **run your setter** (usually what you want — validation on construction). `self._balance = x` skips it. Know which one you're doing.

**Recall prompt:** *Why doesn't Python code need getters the way Java does?*
