## ② Now count the pain

Look at what you just wrote and find these. They're all in there:

```
1.  Every function starts with `users, balances` —
    the same arguments dragged everywhere.

2.  Nothing stops this:
        balances["d"]["p"] = "hello"        ← a string, in a balance
        add_expense(users, balances, "ghost", 500, [...])   ← user doesn't exist

3.  users["d"]["nmae"]     ← typo. Returns nothing. Fails silently.

4.  To add "settle up", you must find and change 3 functions.

5.  Someone reading it cannot tell what a "user" is.
    They have to reconstruct it from the dict keys.
```

**That's the entire case for classes.** Not "encapsulation is a pillar of OOP." This.

## ③ O-03 · Nouns → classes, verbs → methods

**Anchor:** *"Nouns become classes, verbs become methods."*

Read the requirement and literally underline the words:

```
"A USER can ADD an EXPENSE to a GROUP. The expense is SPLIT
 between PARTICIPANTS. Each user has a BALANCE with every other user."

 nouns  → User, Expense, Group, Balance          → candidate classes
 verbs  → add, split, settle                     → candidate methods
```

```
     ┌──────────┐            ┌────────────┐
     │   User   │            │  Expense   │
     │──────────│            │────────────│
     │ name     │            │ amount     │
     │ email    │◄───────────│ paid_by    │
     │ balances │  involved  │ splits     │
     │──────────│            │────────────│
     │ pay()    │            │ split()    │
     └──────────┘            └────────────┘
```

**This is not a metaphor — it's the actual technique** used in LLD interviews. In L13 it becomes step 2 of your 6-step method. Start doing it now.

**Careful:** not every noun becomes a class. "Amount" is a noun and it's just a `float`. A noun earns a class when it has **both data and behaviour**, or when several fields must stay consistent together.

**Recall prompt:** *You're given a two-line requirement. What's the first thing you do with the words?*

## ④ O-04 · Data that travels together

**Anchor:** *"If two variables always travel together, they're one object."*

This is the most practical test you'll learn today.

```python
# smell: these three always appear as a set
def send_invoice(name, email, address): ...
def print_label(name, email, address): ...
def validate(name, email, address): ...

# fix
@dataclass
class Customer:
    name: str
    email: str
    address: str

def send_invoice(customer: Customer): ...
```

**Three signs a class is missing:**

| Sign | Example |
|---|---|
| Same group of parameters everywhere | `(name, email, address)` in five functions |
| A dict whose keys you keep spelling out | `user["name"]`, `user["email"]` |
| A function needing 4+ arguments to do one thing | `add_expense(users, balances, payer, amt, people)` |

Your `v0_procedural.py` has all three. Go and look — actually go and look.

**Recall prompt:** *Name two signs that a class is missing from code.*

## 🔨 Build it — 20 min

### 🔨 Find the objects — on paper first, no code

Take this requirement:

```
A library has books. A member can borrow a book for 14 days.
If returned late, a fine of ₹5 per day is charged.
A member can hold at most 3 books at a time.
```

1. **Underline the nouns.** Write them in a list.
2. Cross out the ones that are just values (`14 days`, `₹5`, `3`).
3. For each survivor, write **what it knows** (data) and **what it does** (verbs).
4. Draw the boxes and the arrows between them.

<details>
<summary>Check yourself — open only after you've written yours</summary>

**Classes:** `Book`, `Member`, `Library`, and probably `Loan` (it holds `book`, `member`, `borrowed_date`, `due_date` — data that always travels together, which is exactly O-04).

**`Loan` is the one most people miss.** It isn't in the text as a noun, but the borrow-date and due-date have to live somewhere, and hanging them on `Book` breaks the moment a book is borrowed twice.

**Verbs:** `borrow()`, `return_book()`, `calculate_fine()`, `can_borrow()`.

If you found 3 of the 4 classes, that's a good first attempt.
</details>
