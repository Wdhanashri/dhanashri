## ① O-09 · Composition

**Anchor:** *"A car HAS an engine. A car IS NOT an engine."*
**Yaad rakho:** *"Gaadi mein engine hai — gaadi engine nahi hai."*

Two ways for class A to use class B. That's the entire decision.

```
COMPOSITION  (has-a)                INHERITANCE  (is-a)

  ┌─────────┐                        ┌──────────┐
  │   Car   │                        │ Vehicle  │
  │─────────│                        └────┬─────┘
  │ engine ─┼──→ ┌────────┐               │ extends
  │ wheels ─┼──→ │ Engine │          ┌────▼─────┐
  └─────────┘    └────────┘          │   Car    │
                                     └──────────┘
  "a Car HAS an Engine"              "a Car IS a Vehicle"
  flexible — swap it anytime         rigid — fixed at write-time
```

### The test, in one question

> **Say it out loud: "A ___ IS A ___."**
> Sounds wrong? → composition.
>
> *"A Car is an Engine"* — wrong. So `Car` **has** an `Engine`.
> *"A Car is a Vehicle"* — fine. So inheritance is allowed (L6 adds a second test).

### Why composition wins

```python
class Car:
    def __init__(self, engine: Engine):
        self.engine = engine            # given from outside

    def start(self):
        self.engine.ignite()

petrol_car = Car(PetrolEngine())
ev         = Car(ElectricEngine())      # same Car class. Different behaviour.
```

**You can change the engine at runtime.** With inheritance you'd need `PetrolCar` and `ElectricCar` as separate classes — and then `ElectricSportsCar`, and then the combinations explode.

This is the actual meaning of the advice **"favour composition over inheritance"** — a line you'll be asked to explain in interviews, and which almost nobody explains beyond quoting it.

### The delegation habit

```python
class Order:
    def __init__(self, customer: Customer, items: list[Item]):
        self.customer = customer
        self.items = items

    def total(self) -> float:
        return sum(item.price for item in self.items)    # ask the items
```

`Order` doesn't know how an item computes its price. It **asks**. Each object holds its own knowledge, and objects talk to each other.

**Recall prompt:** *You need class A to use class B. What sentence do you say out loud to decide how?*

### 🔨 Feel the difference — 10 min

```python
# Model this two ways, in one file:
#
# WAY 1 (inheritance):  class FileLogger, class EmailLogger, class ConsoleLogger
#                       each with a log(msg) method
#                       then class Service(FileLogger) that logs on do_work()
#
# WAY 2 (composition):  class Service that takes a logger object in __init__
#                       and calls self.logger.log(msg)
#
# Now: make a Service that logs to console during a test, and to file in prod.
# Try it with WAY 1. Then with WAY 2.
```

**Acceptance:** you personally hit the wall in WAY 1 — you have to create a whole new class (or edit one) just to change where logs go. In WAY 2 you pass a different object. **That wall is the lesson.**

## ② The three flavours of has-a

You don't need the vocabulary for a fresher interview, but knowing the distinction stops design mistakes:

| Relationship | Meaning | Example |
|---|---|---|
| **Association** | knows about | `Expense` knows its `User`s |
| **Aggregation** | has, but they outlive it | `Group` has `User`s — delete the group, users remain |
| **Composition** | has, and owns their lifetime | `Order` has `OrderLine`s — delete the order, they're gone |

**The useful question:** *if I delete the container, should the contents die too?*

```
Group deleted  →  Users still exist        (aggregation)
Order deleted  →  OrderLines meaningless   (composition)
```

### 🔨 1 — Group, composed of Users

```python
# class Group:
#     __init__(self, group_id: str, name: str)
#         → self.members: list[User] = []
#         → self.expenses: list[Expense] = []
#     __repr__
#     add_member(self, user: User)
#         → raise ValueError if already a member
#     add_expense(self, expense: Expense)
#         → raise ValueError if any participant is not a member
#         → otherwise store it AND update everyone's balances
#     total_spent(self) -> float
#         → delegate: sum of each expense's amount
```

**Acceptance:** adding an expense with an outsider raises. `total_spent()` is one line that asks the expenses.

### 🔨 2 — notice the delegation

> In a comment above `total_spent`, write one sentence: **why doesn't `Group` calculate the amount itself?**

The answer is the habit you're building — *each object owns its own knowledge; others ask.*

### 🔨 3 — swap a component

```python
# Give Group a `splitter` object passed into __init__, with a split(amount, users) method.
```

**Acceptance:** two groups behave differently, and you did not touch the `Group` class between them.
