## Before we start — the honest version

Five principles, and most guides dump all five on you with abstract definitions. You then memorise five acronyms and still can't apply any of them.

**Two of them do most of the real work: SRP and OCP.** Those get this whole session. The other three get L10, framed as one idea, because that's what they actually are.

## ① O-15 · Single Responsibility

**Anchor:** *"Can't describe the class without saying 'and'? It's two classes."*

That's the entire test. Say the class's job out loud:

```
"User stores name and email"                          ✅ one job
"User stores name and email AND sends welcome emails
 AND validates passwords AND saves itself to the DB"  🚩 four jobs
```

Every **"and"** is a class trying to escape.

```python
# 🚩 four responsibilities in one class
class User:
    def __init__(self, name, email): ...
    def send_welcome_email(self): ...       # emailing
    def save_to_database(self): ...         # persistence
    def validate_password(self, pw): ...    # security
```

Why it hurts, concretely:

```
change the email provider  → edit User
change from MySQL to Mongo → edit User
change password rules      → edit User

three unrelated teams, editing the same file, breaking each other
```

```python
# ✅
@dataclass
class User:
    name: str
    email: str

class EmailService:
    def send_welcome(self, user: User): ...

class UserRepository:
    def save(self, user: User): ...

class PasswordValidator:
    def validate(self, pw: str) -> bool: ...
```

### The formal phrasing, for the interview

> *"A class should have only one reason to change."*

Then immediately give the test: *"practically — if I can't describe it without saying 'and', it's doing too much."* The definition alone sounds memorised; the test proves you use it.

### The over-correction (this matters)

Do **not** split every class until each has one method. That produces fifty tiny classes and a design nobody can follow.

> **One coherent responsibility, not one method.** `User` holding name, email *and* a balance is fine — that's all "being a user."

**Recall prompt:** *What's the five-second test for whether a class does too much?*

### 🔨 Find the "and"s — 8 min

```python
class Order:
    def calculate_total(self): ...
    def apply_discount(self, code): ...
    def charge_card(self, card): ...
    def send_confirmation_email(self): ...
    def generate_invoice_pdf(self): ...
    def update_inventory(self): ...
```

> On paper: **describe this class in one sentence.** Count your "and"s.
> Then list the classes that should exist instead. Name them.

<details>
<summary>Check yourself</summary>

`Order` (total, discount) · `PaymentProcessor` (charge) · `NotificationService` (email) · `InvoiceGenerator` (pdf) · `InventoryService` (stock).

**Notice:** `Order` keeps `calculate_total` and `apply_discount` — both are genuinely "being an order." That's the over-correction warning in action; splitting those out too would be worse, not better.

## ② O-16 · Open/Closed

**Anchor:** *"Add a file, don't edit a file."*

> *Open for extension, closed for modification.*

That sentence means nothing on its own. Here's what it means:

```
NEW REQUIREMENT ARRIVES

  ❌ closed design:  open PaymentProcessor.py, add an `elif`,
                     re-test everything, hope you broke nothing

  ✅ open design:    create UpiPayment.py. Touch nothing else.
```

```python
# 🚩 every new method means editing this function
def process_payment(method, amount):
    if method == "card":  ...
    elif method == "upi": ...
    elif method == "netbanking": ...        # edit. again.
```

```python
# ✅
class PaymentMethod(ABC):
    @abstractmethod
    def pay(self, amount: float) -> bool: ...

class CardPayment(PaymentMethod):
    def pay(self, amount): ...

class UpiPayment(PaymentMethod):            # NEW FILE. Nothing else touched.
    def pay(self, amount): ...

def process_payment(method: PaymentMethod, amount: float):
    return method.pay(amount)               # never changes again
```

### Why "don't edit" is the point

Editing working code means **re-testing working code**. Adding a new class means testing only the new thing. In a real codebase that difference is the difference between a one-hour change and a two-day one.

### Notice what OCP is made of

Look at that fix. It's an ABC (L8) plus polymorphism (L7).

**SOLID is not new material.** It's names for the good judgement you've been building for four sessions. If OCP feels familiar, that's because you already wrote it on L5 with the swappable splitter.

### The trap — don't do this everywhere

Making *everything* extensible produces abstraction soup. Apply OCP where **change is actually likely**: payment methods, split types, notification channels, pricing rules. Not to `User.name`.

> **Ask: "will there realistically be a version 2 of this?"** No → leave it concrete.

**Recall prompt:** *When a new requirement arrives, what does an OCP-compliant design let you avoid?*

## 🔨 Build it — 30 min · the big refactor

Create `lld/splitwise/v2_solid.py`. Move your code across, restructured.

### 🔨 1 — split the responsibilities

```python
# Right now something in your code is doing too much — probably Group
# (holds members AND expenses AND updates balances AND validates).
#
# Split into:
#   Group             → membership only
#   BalanceSheet      → who owes whom; the ONLY thing that mutates balances
#   ExpenseValidator  → checks an expense is legal before it's applied
#   ExpenseService    → orchestrates: validate → split → update balances
#
# Each one: describe it in one sentence, no "and". Write that sentence
# as the class docstring. If you can't, the split is wrong.
```

**Acceptance:** five classes, five one-sentence docstrings, zero "and"s.

### 🔨 2 — make it open for extension

```python
# Add a NEW split type — SharesSplit (Dhanashri pays 2 shares, Paritosh 1).
#
# RULE: you may create a new class. You may not edit ANY existing class.
#
# If you have to edit something, your design isn't open. Fix the design,
# then add the feature.
```

**Acceptance:** `git diff` (or your own eyes) shows one new class and no edits to existing ones. **This is the real test of the session** — everything else is theory until this passes.

### 🔨 3 — the sentence to keep

> At the top of `v2_solid.py`, write in one comment: **which class was hardest to split, and why?**

That difficulty is information. Classes that resist splitting usually have tangled state — and noticing that is a design skill worth more than the refactor itself.
