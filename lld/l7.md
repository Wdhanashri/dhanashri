## ① O-12 · One loop, many types

**Anchor:** *"One loop, many types — the if-chain disappears."*
**Yaad rakho:** *"Naam ek, kaam alag."*

### The code you have been writing your whole life

```python
def calculate_amount(split, total, n):
    if split.type == "equal":
        return total / n
    elif split.type == "exact":
        return split.value
    elif split.type == "percent":
        return total * split.percent / 100
    elif split.type == "shares":            # new requirement
        ...                                 # ← EDIT this function. Again.
```

Every new split type means **editing this function**. And there will be four more functions shaped exactly like it — `validate_split`, `display_split`, `serialise_split` — each with the same if-chain, and you will forget to update one of them.

### The replacement

```python
for split in splits:
    print(split.amount())        # each object knows its own answer
```

**One line. Works for every type that exists — and for every type you add later.**

```
       BEFORE                              AFTER

   ┌──────────────┐                   ┌──────────────┐
   │ if equal:    │                   │ split.amount()│
   │ elif exact:  │                   └───────┬──────┘
   │ elif percent:│                           │ Python dispatches
   │ elif shares: │                    ┌──────┼──────┐
   └──────────────┘                    ▼      ▼      ▼
   caller decides                    Equal  Exact  Percent
                                     each decides for itself
```

**The shift:** the caller stops asking *"what type are you?"* and starts saying *"do your thing."* That single change is what polymorphism is.

### Why this is the interview answer

Asked *"what is polymorphism?"*, most candidates say *"one interface, many forms"* — a memorised phrase that demonstrates nothing.

Say this instead:

> *"It lets me replace a type-checking if-chain with a single call, so adding a new type means adding a class instead of editing existing code."*

That answer shows you know what it's **for**.

**Recall prompt:** *What does polymorphism let you delete from your code?*

## ② O-13 · Duck typing

**Anchor:** *"If it has the method, Python doesn't care what class it is."*

In Java, polymorphism requires a shared parent or interface. **Python doesn't.**

```python
class Dog:
    def speak(self): return "bhow"

class Cat:
    def speak(self): return "meow"

class Doorbell:                 # not an animal. Not related to anything.
    def speak(self): return "ding"

for thing in [Dog(), Cat(), Doorbell()]:
    print(thing.speak())        # works. All three.
```

> *"If it walks like a duck and quacks like a duck, treat it as a duck."*

Python checks whether the **method exists**, at the moment you call it. No inheritance needed.

### What this means for your designs

```python
class Group:
    def __init__(self, splitter):
        self.splitter = splitter        # ANY object with .split()

group = Group(EqualSplitter())
group = Group(PercentSplitter())
group = Group(FakeSplitterForTesting())   # ← testing gets easy, free
```

You don't need a base class for this to work. **But you often still want one** — that's L8, and the reason is that a base class turns an unwritten assumption into an enforced promise.

### EAFP — the Python way of asking

```python
# LBYL — "Look Before You Leap"   (the C/Java instinct)
if hasattr(obj, "split"):
    obj.split(...)

# EAFP — "Easier to Ask Forgiveness than Permission"   (the Python instinct)
try:
    obj.split(...)
except AttributeError:
    ...
```

Python prefers EAFP. Worth saying out loud in an interview — it signals you write Python rather than Java-with-Python-syntax.

**Recall prompt:** *Does Python need a shared base class for polymorphism to work?*

### 🔨 1 — polymorphism across the whole Splitwise

```python
# Rewrite Expense so it stores a list[Split] instead of split_type + values.
# Then:
#   Expense.validate() -> bool
#       → sum of all split amounts == self.amount (within 0.01 for floats)
#   Expense.apply(self)
#       → for each split, update balances between split.user and paid_by
#
# BOTH methods must be free of any if-chain on split type.
```

**Acceptance:** grep your own file for `split_type ==`. Zero hits.

### 🔨 2 — the float trap

```python
# Test: a ₹100 expense split equally between 3 people.
# print(33.33 + 33.33 + 33.33 == 100)      → False
# Handle it: compare with a tolerance, OR give the remainder to the payer.
# Pick one, implement it, and write ONE COMMENT saying why you chose it.
```

**Acceptance:** the validation passes for a 3-way split of ₹100.

> **This is a genuine interview follow-up.** *"How do you handle the paisa that doesn't divide?"* Having a real answer — and knowing that floats can't represent money exactly — puts you ahead of most freshers.

### 🔨 3 — duck typing on purpose

```python
# Write class LoggingSplit that WRAPS another split:
#     __init__(self, inner)
#     amount(self) -> float:   prints then returns self.inner.amount()
# It does NOT inherit from Split.
# Confirm it works everywhere a real Split works.
```

**Acceptance:** your `sum(s.amount() for s in splits)` works with a `LoggingSplit` mixed in, despite it having no relationship to `Split`.
