## ① O-20 · Observer

**Anchor:** *"Don't call me — subscribe, and I'll call you."*

### The problem

An expense is added. Now: email everyone, update analytics, refresh the UI, log it for audit.

```python
# 🚩
class ExpenseService:
    def add_expense(self, expense):
        self._save(expense)
        EmailService().send(expense)          # ExpenseService now knows about email
        Analytics().track(expense)            # ...and analytics
        UIRefresher().refresh()               # ...and the UI
        AuditLog().write(expense)             # ...and auditing
```

`ExpenseService` now depends on four unrelated systems. Every new "also do this" means editing it (**OCP violation**) and it now has five jobs (**SRP violation**).

### The fix — invert who knows whom

```python
class Observer(ABC):
    @abstractmethod
    def update(self, event: str, data) -> None: ...

class Subject:
    def __init__(self):
        self._observers: list[Observer] = []

    def subscribe(self, observer: Observer) -> None:
        self._observers.append(observer)

    def notify(self, event: str, data) -> None:
        for o in self._observers:
            o.update(event, data)


class ExpenseService(Subject):
    def add_expense(self, expense):
        self._save(expense)
        self.notify("expense_added", expense)     # ← one line. Forever.
```

```
                    ┌──────────────────┐
                    │  ExpenseService  │
                    │    .notify()     │
                    └────────┬─────────┘
                             │ "expense_added"
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        EmailNotifier   Analytics      AuditLog
        (subscribed)    (subscribed)   (subscribed)

  ExpenseService knows NONE of their names.
  Adding a fifth listener means editing nothing.
```

### Wiring it up

```python
service = ExpenseService()
service.subscribe(EmailNotifier())
service.subscribe(AnalyticsTracker())
service.subscribe(AuditLogger())          # add or remove freely, at runtime
```

## ② Singleton — and why to be careful

**"One instance only."** It's the pattern every fresher name-drops, and the one senior engineers argue about.

```python
class ParkingLot:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

>>> ParkingLot() is ParkingLot()      # True — same object
```

The Pythonic version is usually simpler — **a module is already a singleton**:

```python
# config.py
settings = Settings()          # imported anywhere, created once
```

### The honest problems

| Problem | Why it bites |
|---|---|
| Global state | anyone can change it from anywhere — the exact thing L4 taught you to avoid |
| Untestable | tests share one instance and leak into each other |
| Hides dependencies | a class using a singleton doesn't *declare* that it does |
| Thread-unsafe | naive `__new__` can create two under concurrency |

**Notice that the third one directly contradicts L10's dependency injection.** A singleton is a hidden dependency. That tension is real and worth understanding.

### What to say in an interview

> *"I'd make ParkingLot a singleton since there's one physical lot — but I'd inject it rather than calling `getInstance()` everywhere, so it stays testable."*

That's a nuanced answer. **It's much better than "I used Singleton because there's only one"** — which is what most candidates say and which invites a follow-up they can't handle.

**Use it for:** genuinely-one things (config, connection pool, the lot itself).
**Not for:** convenience, or to avoid passing parameters.
