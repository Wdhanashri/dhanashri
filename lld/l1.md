## ① O-01 · Everything is an object

**Anchor:** *"In Python, everything is an object — even a function, even a class."*

Open a terminal and run this. Actually run it.

```python
>>> type(5)
<class 'int'>
>>> type("hi")
<class 'str'>
>>> type([1,2])
<class 'list'>
>>> def f(): pass
>>> type(f)
<class 'function'>
>>> type(int)
<class 'type'>          # even the class `int` is itself an object
```

You have been using objects since day one. `nums.append(3)` is a method call on a `list` object. `s.upper()` is a method call on a `str` object.

**So classes are not a new, scary thing.** You are just about to make your own versions of the things you already use.

### The part that unlocks everything

When you write `len(x)`, Python actually runs `x.__len__()`. When you write `a + b`, it runs `a.__add__(b)`.

```python
>>> "ab" + "cd"        # runs str.__add__
'abcd'
>>> len([1,2,3])       # runs list.__len__
3
```

**Those `__dunder__` methods are how your class plugs into Python's own syntax.** Define `__len__` on your class and `len()` starts working on it. That's the whole mechanism.

**Recall prompt:** *When you write `len(x)`, what does Python actually call?*

## ② O-02 · dataclass, Enum, type hints

**Anchor:** *"`@dataclass` writes the boring code; `Enum` stops the typos."*

### The boring code, by hand

```python
class Expense:
    def __init__(self, amount, paid_by, description):
        self.amount = amount
        self.paid_by = paid_by
        self.description = description

    def __repr__(self):
        return f"Expense({self.amount}, {self.paid_by}, {self.description})"
```

Nine lines, and every attribute is written **three times**. Now:

```python
from dataclasses import dataclass

@dataclass
class Expense:
    amount: float
    paid_by: str
    description: str = ""
```

Four lines. You get `__init__`, `__repr__` and `__eq__` free.

```python
>>> e = Expense(500, "dhanashri", "dinner")
>>> e
Expense(amount=500, paid_by='dhanashri', description='dinner')
>>> e == Expense(500, "dhanashri", "dinner")
True
```

**Use `@dataclass` for anything that's mostly data.** Write `__init__` by hand only when there's real logic in it — validation, computed fields.

### Enum — the typo killer

```python
# without Enum
expense.split_type = "eqaul"      # typo. Silently wrong. Debug it at 2am.

# with Enum
from enum import Enum

class SplitType(Enum):
    EQUAL = "equal"
    EXACT = "exact"
    PERCENT = "percent"

expense.split_type = SplitType.EQAUL    # AttributeError, immediately
```

**In LLD, use an Enum for every fixed set of options** — vehicle types, order statuses, payment methods. It's a small thing interviewers consistently notice.

### Type hints

```python
def split(amount: float, people: list[str]) -> dict[str, float]:
```

Python ignores them at runtime. Write them anyway: in a design interview they *are* half your documentation, and they make you state what a function actually takes and returns before you write it.

**Recall prompt:** *What three methods does `@dataclass` write for you?*
