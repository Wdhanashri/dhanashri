## ① O-10 · Inheritance

**Anchor:** *"Only inherit when the child is genuinely a *kind of* the parent."*

```python
class Vehicle:
    def __init__(self, plate: str, owner: str):
        self.plate = plate
        self.owner = owner

    def describe(self) -> str:
        return f"{self.__class__.__name__} {self.plate}"

    def spots_needed(self) -> int:
        raise NotImplementedError            # children MUST answer this


class Car(Vehicle):
    def __init__(self, plate: str, owner: str, doors: int = 4):
        super().__init__(plate, owner)       # ← FIRST LINE. Always.
        self.doors = doors

    def spots_needed(self) -> int:
        return 1


class Truck(Vehicle):
    def spots_needed(self) -> int:
        return 2
```

### `super()` — what it does and why it's first

```python
super().__init__(plate, owner)
```

*"Run the parent's `__init__` on me."* Without it, `self.plate` and `self.owner` never get set, and you get an `AttributeError` far away from the real cause.

**Put it first**, before your own attributes. Parent sets up its part, then you add yours.

```
Vehicle.__init__  →  sets plate, owner
        │
        ▼
Car.__init__      →  sets doors
```

### What you inherit

```python
c = Car("MH12AB1234", "Dhanashri")
c.describe()          # ← Vehicle's method. Free.
c.spots_needed()      # ← Car's override wins.
isinstance(c, Vehicle)   # True
```

**Overriding** = same method name, different body. The child's version wins.

**Recall prompt:** *What does `super().__init__()` do, and what breaks if you forget it?*

## ② O-11 · When inheritance is wrong

**Anchor:** *"If you're overriding to *remove* behaviour, it was never is-a."*

This half is worth more than the first half. **Over-inheriting is the classic beginner mistake**, and interviewers probe for it.

### Smell 1 — overriding to disable

```python
class Bird:
    def fly(self): ...

class Penguin(Bird):
    def fly(self):
        raise NotImplementedError("penguins can't fly")   # 🚩
```

A `Penguin` is a `Bird`, but it is **not** a *kind of the thing `Bird` promises*. `Bird` promised flight; `Penguin` withdraws it. Anyone holding a `Bird` and calling `fly()` now crashes.

> **Rule: a child may add and may change *how*. It may never take away.**

Fix: `Bird` doesn't promise flight. `FlyingBird(Bird)` does.

### Smell 2 — inheriting to reuse code

```python
class Stack(list):          # 🚩 "list already has append and pop, free!"
    def push(self, x): self.append(x)
```

You also inherited `insert()`, `remove()`, `sort()`, `[]` indexing — **none of which a stack should allow.** You reused code and destroyed the guarantee.

```python
class Stack:                # ✅ composition
    def __init__(self):
        self._items = []
    def push(self, x): self._items.append(x)
    def pop(self): return self._items.pop()
```

> **Inheritance is for "is-a", never for "I want those methods."** For that, use composition.

### Smell 3 — the deep tree

```
Vehicle → Car → SportsCar → ElectricSportsCar → ...  🚩
```

Three levels or more and nobody can tell where a method comes from. **Two levels is plenty** for a fresher LLD answer.

### The two-part test

```
1. Say "B IS A kind of A."     Sounds wrong → composition.
2. Can B do EVERYTHING A promises, without disabling anything?
                                No → composition.

Both yes → inheritance is safe.
```

Test 2 is Liskov Substitution, arriving four sessions early. When you meet the acronym on L10 you'll already own the idea.

**Recall prompt:** *You're overriding a method to make it raise an error. What does that tell you?*

For each: **inheritance or composition?** One line of reasoning each.

```
1. Admin  /  User
2. Car    /  Engine
3. Square /  Rectangle
4. SavingsAccount / BankAccount
5. Employee / Person
6. Playlist / Song
```

<details>
<summary>Check yourself</summary>

1. **Inheritance.** An Admin is a kind of User, adds permissions, removes nothing.
2. **Composition.** A car has an engine. Says so out loud.
3. **Trick question — composition, or neither.** The famous trap: a `Square` sets width and height together, so `rect.width = 5` behaves differently on a Square. It *breaks* Rectangle's promise. Geometry says is-a; code says no. **Mention this in an interview and you look well-read.**
4. **Inheritance.** Adds interest, removes nothing.
5. **Inheritance** — usually. But if someone can be both Employee and Customer, composition (`Person` has a `Role`) survives better.
6. **Composition.** A playlist *has* songs. Obviously.

Got 4+? Good. Number 3 catches nearly everyone the first time.
</details>

### 🔨 1 — a Split hierarchy

```python
# class Split:                       # base
#     __init__(self, user: User)
#     __repr__
#     amount(self) -> float          → raise NotImplementedError
#
# class EqualSplit(Split):
#     __init__(self, user, total: float, n_people: int)
#     amount(self) -> float          → total / n_people
#
# class ExactSplit(Split):
#     __init__(self, user, value: float)
#     amount(self) -> float          → value
#
# class PercentSplit(Split):
#     __init__(self, user, total: float, percent: float)
#     amount(self) -> float          → total * percent / 100
```

**Acceptance:** all three subclasses call `super().__init__(user)`. Build a list of mixed splits and print each one's `amount()`.

### 🔨 2 — apply the test to your own code

> In a comment above `Split`, answer both parts:
> *"An EqualSplit IS A kind of Split"* — does that sound right?
> Does any subclass *remove* anything the base promised?

If both answers are clean, the inheritance is justified. **Being able to say that out loud is what an interviewer is listening for.**

### 🔨 3 — deliberately do it wrong

```python
# Add class NoSplit(Split) whose amount() raises "this user pays nothing".
# Then write a loop:  total = sum(s.amount() for s in splits)
# Watch it crash when a NoSplit is in the list.
# Then fix it properly — NoSplit should return 0.0, not raise.
```

**Acceptance:** you saw the crash, and you can name the rule it broke.
