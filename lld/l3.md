## ① O-05 · `self`

**Anchor:** *"`self` is whoever the method was called on."*
**Yaad rakho:** *"`self` matlab — jis object pe method call hua, wahi."*

Almost every tutorial says "self refers to the instance" and moves on. That sentence explains nothing. Here's the demonstration that does.

### `self` is not magic — it's the first argument

```python
class User:
    def __init__(self, name):
        self.name = name

    def greet(self):
        print(f"hi, {self.name}")

d = User("Dhanashri")
d.greet()                  # what you write
User.greet(d)              # what Python ACTUALLY runs  ← same thing
```

**Run both lines. They print the same thing.**

```
d.greet()
│
└── Python rewrites this as →  User.greet(d)
                                        │
                                        └── this `d` lands in the parameter
                                            named `self`
```

That's the whole mystery. `self` is an ordinary parameter, and Python fills it in with **the object on the left of the dot**.

### So why write it every time?

Because there could be many objects:

```python
d = User("Dhanashri")
p = User("Paritosh")

d.greet()      # self is d  → "hi, Dhanashri"
p.greet()      # self is p  → "hi, Paritosh"
```

**One class. One `greet` function. Many objects.** The method needs to be told *which* object it's working on — and `self` is how it's told.

### Proof it's just a name

```python
class Weird:
    def __init__(banana, name):     # legal Python. Do NOT do this.
        banana.name = name

    def greet(banana):
        print(banana.name)

Weird("test").greet()               # works fine
```

`self` is a **convention**, not a keyword. Everyone uses it, so you must too — but knowing it's just a name is what removes the mystery.

**Recall prompt:** *`d.greet()` — what does Python actually run?*

## ② O-06 · `__init__` and `__repr__`

**Anchor:** *"`__init__` builds it, `__repr__` shows it to you."*

### `__init__` is not a constructor

Python creates the object first, *then* hands it to `__init__` to fill in.

```python
d = User("Dhanashri")

# what happens:
#   1. Python makes an empty User object
#   2. Python calls  User.__init__(that_object, "Dhanashri")
#   3. your code sets  self.name = "Dhanashri"
#   4. you get the object back
```

Which is why `__init__` **returns nothing.** The object already exists.

```python
def __init__(self, name):
    self.name = name
    return self          # ❌ TypeError. Never do this.
```

### `__repr__` is not optional

```python
class User:
    def __init__(self, name):
        self.name = name

>>> print(User("Dhanashri"))
<__main__.User object at 0x7f3d2c1a4d90>      # useless
```

You will debug this exact uselessness a hundred times. Fix it once, always:

```python
    def __repr__(self):
        return f"User({self.name})"

>>> print(User("Dhanashri"))
User(Dhanashri)
```

**Rule: every class you write gets a `__repr__`.** No exceptions. Debugging a design with anonymous objects is genuinely awful, and it costs you one line.

### `__init__` by hand vs `@dataclass`

```python
@dataclass                    # use when it's mostly data
class Expense:
    amount: float
    paid_by: str

class Expense:                # write it by hand when there's LOGIC
    def __init__(self, amount, paid_by):
        if amount <= 0:
            raise ValueError("amount must be positive")   # ← this is why
        self.amount = amount
        self.paid_by = paid_by
```

**Recall prompt:** *Why does `__init__` return nothing?*

### 🔨 1 — the User class

```python

#     __init__(self, user_id: str, name: str, email: str)
#         → also set self.balances = {}     (other_user_id -> amount)

#     add_balance(self, other_id: str, amount: float)
#         → += into the dict, creating the key if missing
#     total_owed(self) -> float
#         → sum of only the POSITIVE balances (what others owe you)
```

**Acceptance:** create a user, add two balances, print it, get a sensible `total_owed`.

### 🔨 2 — the Expense class

```python
# class Expense:
#     __init__(self, expense_id, amount, paid_by: User, participants: list[User], description="")
#         → raise ValueError if amount <= 0
#         → raise ValueError if paid_by not in participants
#     __repr__
#     split_equally(self) -> dict[str, float]
#         → returns {user_id: share} for everyone
```

**Acceptance:** an amount of `0` raises. A payer outside the participant list raises. Both crashes happen *before* any bad data is stored.

### 🔨 3 — wire it up

```python
# Create 3 users. Create an expense of ₹900 paid by user A, split among all 3.
# Update everyone's balances so that B and C each owe A ₹300.
# Print all three users.
```

**Acceptance:** the numbers are right, and printing a user is readable.
