## ① O-17 · The remaining three

**Anchor:** *"Depend on the promise, not on the class that keeps it."*

L, I and D are three angles on one idea: **code against what something promises, never against what it concretely is.**

---

### L · Liskov Substitution

> *A subclass must be usable anywhere its parent is, without surprises.*

**You already know this.** It's L6's test 2, and the Penguin:

```python
def make_it_fly(bird: Bird):
    bird.fly()

make_it_fly(Penguin())     # 💥 the function did nothing wrong
```

`Penguin` broke the promise `Bird` made. The caller held up its end and still crashed.

**The test:** *swap the child in for the parent everywhere — does anything break?* If yes, it was never a valid is-a.

The classic example, worth having ready:

```python
r = Rectangle(); r.width = 5; r.height = 4      # area 20
s = Square();    s.width = 5; s.height = 4      # area 16 — setting one
                                                # silently changed the other
```

Geometry says a square *is a* rectangle. **Code says no**, because Rectangle promised independent width and height. Mention this in an interview and you sound well-read — it's the canonical LSP example.

### I · Interface Segregation

> *Don't force a class to implement methods it doesn't need.*

```python
# 🚩 one fat interface
class Worker(ABC):
    @abstractmethod
    def work(self): ...
    @abstractmethod
    def eat(self): ...

class Robot(Worker):
    def work(self): ...
    def eat(self):
        raise NotImplementedError    # 🚩 forced into a method that makes no sense
```

```python
# ✅ small interfaces, combined as needed
class Workable(ABC):
    @abstractmethod
    def work(self): ...

class Eatable(ABC):
    @abstractmethod
    def eat(self): ...

class Human(Workable, Eatable): ...
class Robot(Workable): ...
```

**The smell:** a subclass implementing a method with `pass` or `NotImplementedError`. That's the interface being too big — and notice it's the *same* smell as an LSP violation. They're two views of one mistake.

### D · Dependency Inversion

> *Depend on abstractions, not on concrete classes.*

**This is the one that will actually change your code.**

```python
# 🚩 ExpenseService is welded to MySQL and to Gmail
class ExpenseService:
    def __init__(self):
        self.db = MySQLDatabase()          # hard-coded
        self.mailer = GmailSender()        # hard-coded
```

You now cannot test `ExpenseService` without a live MySQL and a real Gmail account. That is how untestable code is born.

```python
# ✅ dependencies handed in from outside
class ExpenseService:
    def __init__(self, db: Database, mailer: Notifier):
        self.db = db
        self.mailer = mailer

service = ExpenseService(MySQLDatabase(), GmailSender())    # production
service = ExpenseService(FakeDatabase(),  FakeMailer())     # tests, instantly
```

This is called **dependency injection**, and the whole thing is: *take it as a parameter instead of creating it inside.*

```
      ┌───────────────┐
      │ ExpenseService│
      └───────┬───────┘
              │ depends on ▼ (the promise)
      ┌───────────────┐
      │  Database ABC │
      └───────┬───────┘
       ┌──────┼──────┐
       ▼      ▼      ▼
    MySQL  Mongo  FakeDB      ← swap freely, service never notices
```

**Say this in an interview:** *"I'd inject the dependency so it's testable."* It's a short sentence that signals real-world experience, and freshers almost never say it.

**Recall prompt:** *Your class creates a `MySQLDatabase()` inside `__init__`. What's wrong, and what's the fix?*

## ② The warning that matters most

**KISS beats SOLID in a 45-minute interview.**

The most common way freshers fail an LLD round is **over-engineering** — bolting on a Factory and an Observer and four ABCs to look impressive. Interviewers read that as "doesn't know when to stop."

```
Start with the simplest thing that works.
Add an abstraction only when you can NAME the change it protects against.
```

If asked *"why didn't you use a Factory here?"*, the right answer is confident, not apologetic:

> *"There's only one kind of user right now, so a Factory would be indirection with no payoff. If we added a second type I'd introduce one."*

**That answer scores better than having built the Factory.** It shows judgement, which is the thing being tested.
