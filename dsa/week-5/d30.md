## ① C-28 · Two heaps

**Anchor:** *"Split the data in half; keep the two halves facing each other."*

```
        SMALL half              LARGE half
        (max-heap)              (min-heap)
                ╲              ╱
          [ ...  9 ]      [ 11  ... ]
                 ▲          ▲
              biggest    smallest
              of small   of large
                 └──  the median lives HERE  ──┘

  equal sizes      → median = (small.top + large.top) / 2
  small has 1 more → median = small.top
```

Both extremes you need are at a heap root, so the median is **O(1)** to read. Inserting is O(log n).

### The code

```python
class MedianFinder:
    def __init__(self):
        self.small = []      # max-heap (store negatives)
        self.large = []      # min-heap

    def addNum(self, num):
        heapq.heappush(self.small, -num)              # always push to small first

        # every element in small must be <= every element in large
        if self.small and self.large and -self.small[0] > self.large[0]:
            heapq.heappush(self.large, -heapq.heappop(self.small))

        # rebalance: sizes differ by at most 1
        if len(self.small) > len(self.large) + 1:
            heapq.heappush(self.large, -heapq.heappop(self.small))
        if len(self.large) > len(self.small):
            heapq.heappush(self.small, -heapq.heappop(self.large))

    def findMedian(self):
        if len(self.small) > len(self.large):
            return -self.small[0]
        return (-self.small[0] + self.large[0]) / 2
```

**Read it as three steps, in this order:** push → fix the ordering → fix the sizes. Doing sizes before ordering gives you a balanced structure holding the wrong numbers.

**The Gotcha:** `small` is a max-heap, so **everything in it is stored negated.** `-self.small[0]` is the real value. Forgetting one minus sign is the bug here, every time — and it produces plausible-looking wrong medians rather than a crash.

**Recall:** *Two heaps for the median — which half is the max-heap, and why is the median O(1)?*

## ② Same tool, disguised · K Closest Points

Not a median problem, but the same instinct: **you don't need the whole sorted order, only the boundary.**

```
distance = x² + y²          ← no square root needed. It doesn't change the ORDER,
                              and skipping it is a nice thing to say out loud.

keep a MAX-heap of size k → evict the farthest → what remains is the k closest
```

That's C-27 with a different comparison. **Notice you already know this** — it's the size-k heap wearing a geometry costume.
