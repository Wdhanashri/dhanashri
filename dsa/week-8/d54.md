## ① C-46 · The LIS shape

**Anchor:** *"`dp[i]` looks back at every `j < i`. Two loops, not one."*

Most 1-D DP looks back a **fixed** distance (`i-1`, `i-2`, `i-coin`). This family looks back at **everything** — a different shape, and worth naming.

> `dp[i]` = **the length of the longest increasing subsequence ENDING at index i.**

```
nums:  [10, 9, 2, 5, 3, 7]
dp:    [ 1, 1, 1, 2, 2, 3]
                 ▲     ▲
                 │     └─ 7 extends 5 (or 3) → dp = 2+1 = 3
                 └─ 5 extends 2 → dp = 1+1 = 2

answer = max(dp), NOT dp[-1]     ← the best run may not end at the last element
```

```python
dp = [1] * len(nums)
for i in range(len(nums)):
    for j in range(i):                      # ← look back at ALL previous
        if nums[j] < nums[i]:
            dp[i] = max(dp[i], dp[j] + 1)
return max(dp)
```

**Two things people get wrong, both worth memorising:**
```
dp[i] = LIS ENDING at i     (not "in the first i elements")
answer = max(dp)            (not dp[-1])
```

**The Gotcha:** because `dp[i]` is defined as *ending at i*, the final answer is the **max over the whole array**. If you define it as "best in the first i" instead, the recurrence gets messier — this is exactly why the English sentence (C-44) has to come first.

**Worth one sentence in an interview:** *"There's also an O(n log n) version using binary search on a 'tails' array."* Don't code it; naming it is enough.

**Recall:** *In LIS, what does `dp[i]` mean, and why isn't the answer `dp[-1]`?*

## ② Subset sum — a boolean DP

**Partition Equal Subset Sum.** Can you split the array into two equal-sum halves?

```
1. total is odd  →  impossible. Return immediately.
2. otherwise, the real question is:
      "can any subset sum to total // 2?"
```

**That reframe is the whole problem.** Once you see it as *subset sum to a target*, the DP is standard:

```python
total = sum(nums)
if total % 2:
    return False
target = total // 2

possible = {0}                      # sums we can currently make
for n in nums:
    possible |= {p + n for p in possible if p + n <= target}
return target in possible
```

**Read the set as the DP state:** *"every sum reachable using the numbers seen so far."* Each new number either joins a sum or doesn't — which is take-or-skip (D51) again, on sums instead of positions.

**The Gotcha:** the `<= target` filter isn't an optimisation — without it the set grows to every reachable sum and the whole thing blows up on large inputs.

**Recall:** *Partition Equal Subset — what's the reframe that makes it a standard DP?*
