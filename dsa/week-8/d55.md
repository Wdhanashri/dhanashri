## ① C-47 · One or two at a time

**Anchor:** *"Take one digit, or take two — if the two are legal."*

**Decode Ways.** `A=1 … Z=26`, so a digit pair is only valid if it's `10–26`.

> `dp[i]` = **the number of ways to decode `s[i:]`.**

```
"226"

at index 0:  take "2"   → legal (2 = B)   → ways = dp[1]
             take "22"  → legal (22 = V)  → ways += dp[2]

at index 1:  take "2"   → legal           → dp[2]
             take "26"  → legal           → dp[3] = 1 (empty = one way)

dp = [3, 2, 1, 1]      answer = dp[0] = 3
```

```python
@cache
def dfs(i):
    if i == len(s):   return 1        # reached the end: one valid decoding
    if s[i] == "0":   return 0        # ← nothing starts with 0

    ways = dfs(i + 1)                                   # take one digit
    if i + 1 < len(s) and (s[i] == "1" or
                          (s[i] == "2" and s[i+1] in "0123456")):
        ways += dfs(i + 2)                              # take two digits
    return ways
```

**Three base cases, and all three matter:**
```
i == len(s)   → 1     an empty remainder is ONE valid decoding, not zero
s[i] == "0"   → 0     no letter is "0", and nothing legal starts with it
two digits    → only "10"–"26"
```

**The Gotcha:** `"0"` alone is invalid, and so is `"06"` — but `"10"` and `"20"` are fine. The zero handling is where every wrong submission comes from, and the tests are full of them.

**Recall:** *Decode Ways — why does reaching the end return 1 rather than 0?*

## ② The running value that flips

**Maximum Product Subarray.** Kadane's logic (which you'll meet properly on D64) breaks here for one reason:

```
[2, -3, -4]

running max:  2 → then -3 makes it -6 → looks terrible
              but -6 × -4 = 24        ← the WORST value became the BEST

a big negative is one multiplication away from being a big positive
```

**So track both extremes:**

```python
res = max(nums)
cur_max = cur_min = 1
for n in nums:
    tmp = cur_max * n                                   # ← save it first
    cur_max = max(n * cur_max, n * cur_min, n)
    cur_min = min(tmp,        n * cur_min, n)
    res = max(res, cur_max)
return res
```

**Two details that are the whole problem:**
```
tmp        cur_max is overwritten before cur_min needs it. Save it.
`n` alone  each max/min includes n by itself — that's the "start fresh here"
           option, and it's what handles zeros correctly
```

**The Gotcha:** without `tmp`, `cur_min` uses the *new* `cur_max`. The code runs, produces sensible-looking numbers, and is wrong on roughly a third of cases.

**Recall:** *Max Product Subarray — why must you track the minimum too?*
