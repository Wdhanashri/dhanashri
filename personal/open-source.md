# preCICE — the deep defence

**~75 min to build. Then 3 minutes before every interview.**

> **This is your strongest card.** Very few freshers have merged PRs in a real open-source project with maintainer review. But a card you can't play is worthless — if you mention it and then can't answer three follow-ups, it becomes a liability instead.
>
> **The bar is not "expert."** The bar is: explain what you changed, why, and what you learned — and say *"I'd have to check"* cleanly on anything else. That's genuinely enough. Don't overinvest past it.

---

## ⓪ Pretest — 3 min. **Write a guess.**

1. In one sentence a non-specialist would understand — what is preCICE?
2. Why did the QR codes on the site break in the first place?

---

## ① The three versions

You need the same story at three lengths. Which one you give depends on how they asked.

### 30 seconds — when it comes up in passing

> *"preCICE is an open-source library for coupling different simulation solvers — the kind researchers use in multi-physics work. I contributed to their documentation website, which is a Jekyll site. Four of my PRs got merged: fixing a broken QR-code feature, cleaning up some third-party dependencies for privacy, and a modernization prototype."*

### 2 minutes — when they say "tell me about it"

Structure it as **one problem, properly**. Don't list all four PRs — pick the QR fix and go deep. Depth on one beats a tour of four.

> *"The site generates printable documentation pages, and each one had a QR code so that if you're reading a printout you can scan it and land on the live page. That had silently broken — the QR images were generated by Google's Charts API, which Google deprecated and turned off, so the images just stopped rendering.*
>
> *I replaced it with `qrcode-generator`, a small client-side JavaScript library, so the code is generated in the browser instead of being fetched from a third party. I also added print-only CSS so the QR block shows up when the page is printed but doesn't clutter the screen version.*
>
> *The part I found most valuable was the review. I opened a PR, a maintainer came back with feedback, and I went through a couple of rounds before it merged. That was the first time I'd had my code reviewed by someone who didn't know me and had no reason to be gentle about it."*

## ② What preCICE actually is

**You do not need to understand computational fluid dynamics.** You need one honest sentence and the confidence to stop there.

```
preCICE = a coupling library for partitioned multi-physics simulation

  a fluid solver  ───┐
                     ├──►  preCICE passes data between them, in step
  a structural    ───┘      so they can simulate one combined problem
  solver
```

> *"It's used when you want to simulate something involving two different physics — say, water flowing over a flexible surface. Rather than one giant program, you keep the specialist solvers separate and preCICE handles the coupling between them."*

**Then stop.** If they push further:

> *"I worked on the documentation website rather than the simulation core, so I know it at that level rather than the numerics."*

**That answer is completely fine and completely honest.** Trying to bluff CFD is how this goes badly.

## ③ The technical questions — with answers

### Q · "What is Jekyll?"
> *"A static site generator. You write content in Markdown, it builds plain HTML at build time, and there's no server or database at runtime. GitHub Pages uses it natively, which is why a lot of documentation sites are built on it."*

**Follow-up: "Static vs dynamic?"** — Static: pages built once at deploy, served as files. Fast, cheap, hard to attack (no server-side code, no DB). Dynamic: built per request, needed when content is personalised.

### Q · "Why did the QR codes break?"
> *"They were generated by Google's Chart API, which Google deprecated and eventually shut down. The site was requesting an image from a URL that no longer served one, so nothing rendered."*

**The lesson to name out loud:** *"It's a good example of why depending on a third-party service for something you can do locally is a risk — the dependency can disappear without you doing anything wrong."* **That sentence is what makes this a good answer instead of a bug report.**

### Q · "Why that library, and why client-side?"
```
✔ generates in the browser  →  no external request, nothing to go down
✔ no API key, no rate limit, no tracking of who printed which page
✔ small and dependency-free
✔ pinned to v1.4.4  →  a build won't break because of an upstream change
```

### Q · "What is print-only CSS?"
> *"A `@media print` block. Styles inside it only apply when the page is being printed, so I could show the QR block on paper and hide it on screen."*

```css
@media print {
  .qr-code { display: block; }
  .site-nav { display: none; }     /* strip nav, sidebars, buttons from paper */
}
```

### Q · "Why remove `jquery.cookie`?"
> *"It was unmaintained — no updates for years — and the site didn't really need it. An unmaintained dependency is a standing risk: nobody's shipping security fixes for it. Removing it was simpler than keeping it."*

**Follow-up: "How did you know it wasn't needed?"** — Search the codebase for every usage, check what each one does, confirm nothing breaks without it. Say that plainly.

### Q · "What does 'cookieless' mean and how did you verify it?"
> *"The site aims not to set tracking cookies. I checked by opening DevTools → Application → Cookies on a fresh profile, and watching the Network tab for third-party requests. Algolia handles the search and Plausible does the analytics, and both can run without setting cookies."*

**Follow-up: "Plausible vs Google Analytics?"** — Plausible is privacy-first: no cookies, no cross-site tracking, much lighter script, and easier under GDPR. Google Analytics gathers far more and sets identifiers.

### Q · "How does the dark-mode toggle work?"
```css
:root              { --bg: #fff; --text: #111; }
:root[data-theme="dark"] { --bg: #111; --text: #eee; }

body { background: var(--bg); color: var(--text); }
```
> *"Colours are CSS custom properties on the root element. The toggle flips a `data-theme` attribute, so every colour swaps at once without touching individual rules. I stored the choice in `localStorage` so it survives a reload."*

**Two follow-ups worth having ready:**

- **"Why `localStorage` and not a cookie?"** → *"It stays in the browser and isn't sent with every request — which fits a site that's deliberately trying to be cookieless. A cookie would have worked but it's the wrong tool here."*
- **"What about the flash of the wrong theme on load?"** → *"You read `localStorage` and set the attribute in a small inline script in the `<head>`, before the body renders. If you wait for a deferred script, users see a white flash first."*

> That second one is a genuinely good detail to mention **unprompted**. It's the kind of thing that separates someone who built it from someone who read about it.

### Q · "The contributors section — how?"
> *"The GitHub REST API exposes a contributors endpoint for a repo. I fetched it and rendered the list. On a static site there's no backend, so it's a client-side fetch."*

**Follow-up: "Rate limits?"** — Unauthenticated GitHub API calls are limited per IP. For production you'd cache the response or fetch at build time rather than on every page load. **Say that** — it shows you thought past the demo.

### Q · "Why Netlify for the demo?"
> *"It deploys a static site straight from a Git branch with a public URL, which made it easy to show maintainers a working version rather than describing it in an issue."*

## ⑤ Why this matters — the sentence to close on

When they ask *"what did you learn?"*, don't say "collaboration." Say something they'd believe:

> *"Two things. Writing code that someone else has to review changes how you write it — I spent much more time reading the existing code before touching it than I would on my own project. And I learned that a small, well-scoped change gets merged, while a big one sits in review. My modernization prototype is still a prototype for exactly that reason."*

**That last clause is honest and it's strong.** It shows you know the difference between doing work and getting work accepted — which is a real engineering distinction most freshers haven't met yet.
