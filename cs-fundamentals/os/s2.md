## OS-05 · Race condition & critical section

**Anchor:** *"Two threads, one variable, and the answer depends on luck."*

```
balance = 100.  Two threads each add 50. Expected: 200.

Thread A                    Thread B
read balance  → 100
                            read balance  → 100     ← same stale value
add 50        → 150
                            add 50        → 150
write 150                                            
                            write 150               ← final answer: 150. Wrong.
```

**Why it happens:** `balance += 50` looks like one step. It's **three** — read, modify, write. The OS can preempt between any two of them.

**Critical section** = the code that touches shared data. It needs three guarantees:

| Requirement | Meaning |
|---|---|
| **Mutual exclusion** | only one thread inside at a time |
| **Progress** | if it's free, someone waiting gets in |
| **Bounded waiting** | nobody waits forever |

**The Gotcha:** race conditions are *intermittent*. The code passes a hundred times and fails on the hundred-and-first. That's exactly why they're feared — and why interviewers like asking about them.

**🎤 Say it:** *"A race condition is when the result depends on the timing of threads. It happens because operations that look atomic — like `x += 1` — are actually read-modify-write, and a thread can be preempted in the middle."*

**Recall:** *Why is `x += 1` not safe between two threads?*

## OS-06 · Mutex vs Semaphore

**Anchor:** *"Mutex is one key. Semaphore is N keys."*
**Yaad rakho:** *"Mutex = ek chabi. Semaphore = N chabiyan."*

```
MUTEX                            SEMAPHORE (counting, N=3)
┌──────────┐                     ┌──────────┐
│  1 key   │                     │  3 keys  │
└────┬─────┘                     └────┬─────┘
     │ only the thread that           │ any thread can signal
     │ locked it may unlock it        │ (it's just a counter)
     ▼                                ▼
  one room, one person            three parking spots
```

| | Mutex | Semaphore |
|---|---|---|
| Value | locked / unlocked | integer count |
| Purpose | **mutual exclusion** | mutual exclusion **or signalling** |
| Ownership | **yes** — only the locker unlocks | **no** — anyone can signal |
| Binary version | that's a mutex | binary semaphore ≈ mutex, minus ownership |

**Semaphore operations:** `wait()` / `P()` decrements (blocks at 0). `signal()` / `V()` increments.

**The interview answer (this is the one they want):**
> *"The key difference is ownership. A mutex must be released by the thread that acquired it, so it's for protecting a resource. A semaphore is just a counter and anyone can signal it — so it also works for signalling between threads."*

**Producer–Consumer, in one picture:**
```
producer → [ buffer ] → consumer

empty  = semaphore(N)   ← how many slots free
full   = semaphore(0)   ← how many items ready
mutex  = mutex(1)       ← protects the buffer itself
```
Producer: `wait(empty) → lock → add → unlock → signal(full)`. Consumer is the mirror image.

**The Gotcha:** the order matters. **Lock the mutex *after* the semaphore wait, never before** — do it the other way and you sleep holding the lock, which is a deadlock.

**Recall:** *Mutex vs semaphore — what's the one word that separates them?*

> ✍️ **Blank page, 3 min.** The comparison table + the producer-consumer three-variable picture.

## OS-07 · Deadlock — the four conditions

**Anchor:** *"You let go first. No, you let go first."*
**Yaad rakho:** *"Tu pehle chhod — nahi, tu pehle chhod."*

```
   Thread A holds  R1  ──wants──→  R2
                    ▲               │
                    │               │
                  wants           holds
                    │               ▼
   Thread B  ←──────────────────── R2

   circular wait. Neither will let go. Both wait forever.
```

**All four must hold at once.** Break any one and deadlock is impossible.

| # | Condition | Meaning |
|---|---|---|
| 1 | **Mutual exclusion** | resource can't be shared |
| 2 | **Hold and wait** | holding one, waiting for another |
| 3 | **No preemption** | can't forcibly take it away |
| 4 | **Circular wait** | A waits for B waits for … waits for A |

**Memory hook: M-H-N-C** → *"Mutual Hold, No Circle-break."*

**Deadlock vs starvation — they get confused constantly:**
```
DEADLOCK    → nobody moves. Ever. Circular.
STARVATION  → others move, one unlucky process never gets a turn.
```

**The Gotcha:** the four conditions are **necessary together, not individually**. Every mutex in your code satisfies condition 1 — that alone is not a deadlock. Say "all four simultaneously," always.

**🎤 Say it:** *"Deadlock needs four conditions at once — mutual exclusion, hold and wait, no preemption, and circular wait. Break any single one and it can't happen."*

**Recall:** *Name the four conditions. Do they need to hold together or separately?*

## OS-08 · Handling deadlock

**Anchor:** *"Prevent it, dodge it, detect it — or ignore it."*

| Strategy | How | Cost |
|---|---|---|
| **Prevention** | design so one of the 4 can never hold | restrictive, wastes resources |
| **Avoidance** | check before granting: is this still safe? (**Banker's**) | must know max needs up front |
| **Detection + recovery** | let it happen, find the cycle, kill or roll back | recovery is disruptive |
| **Ostrich algorithm** | ignore it, reboot if needed | **what Linux and Windows actually do** |

**Prevention, per condition:**
```
1. mutual exclusion → make resources shareable (often impossible)
2. hold and wait    → request EVERYTHING up front, or nothing
3. no preemption    → allow the OS to take resources back
4. circular wait    → impose a global ORDER: always lock R1 before R2  ← the practical one
```

**Banker's algorithm, in one line:** before granting a request, pretend you granted it — if there's still some order in which every process could finish (a **safe sequence**), grant it. Otherwise make it wait.

**The Gotcha:** *"Which does a real OS use?"* — **the ostrich algorithm.** Real systems mostly ignore deadlock, because prevention is expensive and deadlocks are rare. Saying this shows you know theory *and* practice, and it's a genuinely good answer.

**Recall:** *Which of the four conditions is the practical one to break, and how?*
