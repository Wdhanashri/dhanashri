## OS-09 · Virtual memory — why it exists

**Anchor:** *"Small desk, many books — only what you need is on the desk."*
**Yaad rakho:** *"Mez chhoti, kitaabein zyada — jo chahiye wahi mez pe."*

```
   PROCESS sees                        REALITY
   ┌─────────────┐                ┌──────────────┐
   │ 0 ────────► │  contiguous    │ RAM (small)  │  scattered
   │   4 GB      │  private       │ ┌──┐  ┌──┐   │  shared
   │   address   │  huge          │ └──┘  └──┘   │  ├─ page table
   │   space     │                ├──────────────┤  │  maps them
   └─────────────┘                │ DISK (swap)  │  ◄┘
                                  └──────────────┘
```

**Three reasons it exists — this is the interview answer:**

| Reason | What it buys |
|---|---|
| **Run bigger than RAM** | keep only the active pages in memory, rest on disk |
| **Isolation** | process A literally cannot address process B's memory |
| **Simplicity** | every program thinks it starts at address 0 — no relocation maths |

**Logical (virtual) address** = what the process uses. **Physical address** = actual RAM. The **MMU** translates, using the page table, in hardware, on every single memory access.

**The Gotcha:** most people say only "run programs bigger than RAM." **Isolation is arguably the bigger win** — it's why a crashing program can't take down the machine. Say both.

**Recall:** *Give three reasons virtual memory exists.*

> ✍️ **Blank page, 3 min.** Draw the virtual→physical picture. Write all three reasons.

## OS-10 · Paging vs segmentation · fragmentation

**Anchor:** *"Paging cuts by size. Segmentation cuts by meaning."*

```
PAGING                              SEGMENTATION
fixed 4KB chunks, no meaning        variable, logical units

┌────┬────┬────┬────┐               ┌──────┬───┬─────────┐
│ p0 │ p1 │ p2 │ p3 │               │ code │stk│  heap   │
└────┴────┴────┴────┘               └──────┴───┴─────────┘
 all the same size                   each a different size
```

| | Paging | Segmentation |
|---|---|---|
| Size | fixed | variable |
| Divided by | the OS, arbitrarily | the program's logical parts |
| Suffers from | **internal** fragmentation | **external** fragmentation |
| Visible to programmer | no | yes |

**Fragmentation — the pair people mix up:**
```
INTERNAL: you get a whole 4KB page, use 3KB.  1KB wasted INSIDE your block.
          → paging's problem

EXTERNAL: total free memory is plenty, but it's in scattered small gaps
          and no single gap is big enough.
          → segmentation's problem.  Fix: compaction.
```

**The Gotcha:** *"Which is used today?"* — **paging**, essentially everywhere. Segmentation survives only in vestigial form on x86. Fixed-size blocks make allocation trivial, and internal fragmentation (a few KB) is far cheaper than external.

**Recall:** *Internal vs external fragmentation — which belongs to paging?*

> ✍️ **Blank page, 3 min.** The two diagrams + which fragmentation goes with which.

## OS-11 · Page fault & the TLB

**Anchor:** *"Not in RAM? Stop everything, fetch it from disk, resume."*

```
CPU wants virtual address
        │
        ▼
   ┌─────────┐  hit (~1ns)
   │   TLB   │──────────────────────────────► physical address ✅
   └────┬────┘   a small cache of recent translations
        │ miss
        ▼
   ┌────────────┐  valid bit = 1
   │ page table │─────────────────────────────► physical address ✅
   └─────┬──────┘
         │ valid bit = 0  →  PAGE FAULT
         ▼
   trap to OS → find the page on disk → evict someone if RAM is full
              → load it → update the page table → RESTART the instruction
                                                          ~10 million× slower
```

**TLB (Translation Lookaside Buffer)** = a small, very fast cache of recent virtual→physical translations. Without it, every memory access needs an *extra* memory access to read the page table — you'd halve your speed.

**A page fault is not an error.** It's the normal mechanism by which pages arrive in RAM. Only an invalid address is an actual error (that's a segfault).

**The Gotcha:** the instruction is **restarted**, not resumed from the middle. And this is why the TLB gets flushed on a context switch (OS-02) — the new process has a completely different mapping, so every cached translation is now wrong.

**Recall:** *What does the TLB cache, and why would things be twice as slow without it?*

> ✍️ **Blank page, 4 min.** Draw the whole path: CPU → TLB → page table → disk. Label the fault.

## OS-12 · Page replacement & thrashing

**Anchor:** *"RAM is full. Someone has to go — pick wrong and you pay ten million cycles."*

| Algorithm | Rule | Note |
|---|---|---|
| **FIFO** | evict the oldest | suffers **Belady's anomaly** |
| **Optimal (OPT)** | evict what's needed furthest in the future | impossible — needs the future. Used as a benchmark. |
| **LRU** | evict least recently used | the practical choice; approximates OPT |

**Belady's anomaly:** with FIFO, **more frames can cause more page faults.** It's counterintuitive, which is exactly why it gets asked. LRU and OPT never suffer it.

### Thrashing

**Anchor:** *"More time swapping than working."*
**Yaad rakho:** *"Kaam kam, saaman badalna zyada."*

```
CPU
utilisation
    │      ╱╲
    │    ╱   ╲            ← the cliff. Add more processes past this
    │  ╱      ╲              point and throughput COLLAPSES.
    │╱         ╲___________
    └────────────────────── degree of multiprogramming
```

**Why the collapse:** too many processes → each gets too few frames → constant page faults → CPU sits idle waiting on disk → the OS sees low CPU use and *starts more processes* → worse. A death spiral.

**Fixes:** working-set model (give each process the frames it actually needs), page-fault frequency control, or simply suspend some processes.

**The Gotcha:** the cruel part is the feedback loop — **the OS's own response makes it worse.** That detail is what turns a memorised answer into an understood one.

**Recall:** *What is thrashing, and why does adding processes make it worse rather than better?*

> ✍️ **Blank page, 4 min.** Draw the thrashing curve. Write the death-spiral in three arrows.
