## OS-01 · Process vs Thread

**Anchor:** *"Processes are separate houses. Threads are rooms in one house."*

```
   PROCESS A              PROCESS B          ← separate memory. Can't
   ┌──────────┐           ┌──────────┐         touch each other.
   │ code     │           │ code     │
   │ data     │           │ data     │
   │ ┌──┬──┐  │           │ ┌──┐     │
   │ │T1│T2│  │           │ │T1│     │  threads INSIDE share
   │ └──┴──┘  │           │ └──┘     │  code + data + files
   └──────────┘           └──────────┘  but each has its OWN
                                          stack + registers + PC
```

**Why threads exist:** creating a process is expensive (new memory space, new page tables). A thread reuses all of it — so it's cheap to create and cheap to switch between.

| | Process | Thread |
|---|---|---|
| Memory | own | **shared** |
| Creation | expensive | cheap |
| Crash | doesn't affect others | **kills the whole process** |
| Communication | IPC needed (slow) | shared memory (fast) |
| Own stack/registers/PC | yes | **yes** |

**The Gotcha:** threads share memory — *that's the feature and the bug.* Sharing is why they're fast to communicate, and exactly why race conditions exist (OS-05).

**🎤 Say it:** *"A process has its own memory; threads live inside a process and share it. Threads are cheaper to create and switch, but because they share memory you need synchronisation."*

**Recall:** *What do threads share, and what do they keep private?*

> ✍️ **Blank page, 2 min.** Draw the two-house diagram. List what threads share vs own.

## OS-02 · Context switch — and why it costs

**Anchor:** *"Save everything, load everything else — and the cache goes cold."*

```
Process A running          →  interrupt  →       Process B running
       │                                                 ▲
       ▼                                                 │
  save A's registers, PC, stack ptr  ──→ into A's PCB    │
  load B's registers, PC, stack ptr  ←── from B's PCB ───┘
  switch page tables · flush the TLB
  CPU cache now full of A's data → useless for B
```

**PCB (Process Control Block)** = the OS's record card for a process: PID, state, registers, PC, memory map, open files. **The context switch is literally "write into A's PCB, read from B's PCB."**

**Process states — draw this:**
```
  NEW → READY ⇄ RUNNING → TERMINATED
          ↑        ↓
          └─── WAITING ←  (I/O, or waiting for an event)
```
The one people get wrong: **RUNNING → READY** happens when the time slice expires (preemption). **RUNNING → WAITING** happens on I/O. Different arrows, different causes.

**Why it costs (THE interview question):** *"It's pure overhead — no user work happens during it. You save and restore registers, switch page tables, flush the TLB, and worst of all the CPU cache is now full of the old process's data, so the new one starts with cache misses."*

**The Gotcha:** the register save/restore is fast. **The cache going cold is the expensive part** — say that and you're immediately ahead of most candidates.

**Recall:** *Why does a context switch cost time? Give the expensive part.*

> ✍️ **Blank page, 3 min.** Draw the state diagram. Write the 4 things that happen in a switch.

## OS-03 · CPU scheduling

**Anchor:** *"Who runs next, and can you interrupt them?"*

| Algorithm | Rule | Problem |
|---|---|---|
| **FCFS** | first come, first served | **convoy effect** — one long job blocks everyone |
| **SJF** | shortest job first | **starvation** of long jobs; you can't know burst time in advance |
| **SRTF** | preemptive SJF | same, plus more switching |
| **Round Robin** | each gets a time slice `q` | small `q` → too many context switches; large `q` → becomes FCFS |
| **Priority** | highest priority first | starvation → fix with **ageing** (raise priority as it waits) |

```
FCFS,  bursts [20, 2, 2]:      P1────────────────────P2──P3
                               avg wait ≈ 14         ← convoy effect

SJF,   same bursts:            P2──P3──P1────────────────────
                               avg wait ≈ 1.3        ← much better
```

**Preemptive vs non-preemptive:** can the OS *take the CPU away* mid-execution?
- **Preemptive** (RR, SRTF) — yes. Better response time. Needs synchronisation.
- **Non-preemptive** (FCFS, SJF) — no, runs till it blocks or finishes. Simple, but one hog freezes the system.

**The Gotcha:** *"Which is best?"* has no answer. **Batch systems → throughput (SJF). Interactive systems → response time (RR).** Say the trade-off; that's what's being asked.

**🎤 Say it:** *"Round Robin gives everyone a time slice — good response time, but too small a slice means the CPU spends its time context-switching instead of working."*

**Recall:** *What's the convoy effect, and which algorithm suffers from it?*

> ✍️ **Blank page, 3 min.** Table of 5 algorithms + the problem with each.

## OS-04 · User mode, kernel mode, system calls

**Anchor:** *"Your code can't touch hardware. It has to ask."*

```
  ┌─────────────────────────────┐
  │  USER MODE                  │   your program. Restricted.
  │  printf("hi")               │   cannot touch disk, memory maps, devices
  └────────────┬────────────────┘
               │ system call  (write())  ← the ONLY door
  ┌────────────▼────────────────┐
  │  KERNEL MODE                │   the OS. Full hardware access.
  └─────────────────────────────┘
```

**Why two modes exist:** so a buggy or malicious program can't crash the machine or read another process's memory. The CPU has a mode bit; privileged instructions only run when it's set to kernel.

**Common system calls:** `fork()` (make a process), `exec()` (replace it with a new program), `wait()`, `open/read/write`, `exit()`.

**`fork()` — the classic question:**
```python
fork()            # returns 0 in the CHILD, child's PID in the PARENT, -1 on failure
```
The child gets a *copy* of the parent's memory. Modern systems use **copy-on-write** — don't actually copy until someone writes.

**The Gotcha:** a system call is **not** a function call. It's a controlled switch into kernel mode with a mode change and a privilege check — which is why it's slower than a normal call.

**Recall:** *Why does the CPU have two modes at all?*

> ✍️ **Blank page, 2 min.** Draw the two-mode diagram. Write what `fork()` returns to each side.

## 🔥 Rapid fire — 15 min. Notes CLOSED. Say answers OUT LOUD.

60 seconds each. Anything vague → `mistakes.md`.

1. What do threads share? What do they keep private?
2. Why is creating a thread cheaper than creating a process?
3. What's in a PCB?
4. Draw the process state diagram. What causes RUNNING → READY?
5. Why does a context switch cost time — what's the *expensive* part?
6. What's the convoy effect?
7. Why can SJF starve a process?
8. Round Robin: what happens if the time slice is too small? Too large?
9. How do you fix starvation in priority scheduling?
10. Preemptive vs non-preemptive — one sentence.
11. Why does the CPU have user and kernel modes?
12. What does `fork()` return, and to whom?

<details>
<summary>Answers — check only after you've said all 12</summary>

1. Share: code, data, heap, open files. Private: stack, registers, program counter.
2. No new memory space or page tables — it reuses the parent process's.
3. PID, state, registers, PC, memory map, open files, priority.
4. NEW→READY⇄RUNNING→TERMINATED, plus RUNNING→WAITING→READY. RUNNING→READY = time slice expired (preemption).
5. Saving/restoring registers, switching page tables, flushing the TLB — **and the CPU cache going cold**, which is the expensive part.
6. FCFS: one long job at the front makes everyone behind it wait.
7. Short jobs keep arriving and keep jumping the queue.
8. Too small → context-switch overhead dominates. Too large → degenerates into FCFS.
9. Ageing — increase a process's priority the longer it waits.
10. Preemptive: the OS can take the CPU away mid-run. Non-preemptive: it runs until it blocks or finishes.
11. So user programs can't touch hardware or other processes' memory directly — isolation and protection.
12. `0` to the child, the child's PID to the parent, `-1` on failure.
</details>
