## CN-05 · DNS resolution

**Anchor:** *"The internet's phone book — names in, IP addresses out."*

```
you type "google.com"
      │
      ▼
 ① browser cache        already know it? done.
      │ no
 ② OS cache / hosts file
      │ no
 ③ RESOLVER  (your ISP's DNS server) — does the real work:
      │
      ├──► ROOT server (.)          "ask the .com server, here's its address"
      ├──► TLD server (.com)        "ask google's nameserver"
      └──► AUTHORITATIVE server     "google.com = 142.250.183.14"  ✅
      │
      ▼  cached at every level on the way back (TTL controls how long)
```

**Three names to get right:** **root** (knows the TLDs) → **TLD** (knows each domain's nameserver) → **authoritative** (holds the actual record).

**Record types worth knowing:** `A` (name→IPv4) · `AAAA` (IPv6) · `CNAME` (alias) · `MX` (mail) · `NS` (nameserver).

**Recursive vs iterative:** your resolver does the chasing *for* you (recursive). The servers it asks just point it onward (iterative) rather than fetching the answer themselves.

**The Gotcha:** DNS runs over **UDP** (port 53), because a lookup is one small request and one small reply — a TCP handshake would triple the cost. It switches to TCP for large responses (zone transfers). This is a great detail to drop unprompted.

**Recall:** *Name the three server levels in a DNS lookup, in order.*

> ✍️ **Blank page, 4 min.** Draw the full lookup chain from browser cache to authoritative.

## CN-06 · "What happens when you type google.com" ⭐

**Anchor:** *"Resolve, connect, secure, request, render."*

**This is the flagship networking question.** It's loved because it touches every layer at once, and the interviewer can stop you at any point and go deeper. Learn it as **five stages** — five is memorable, twenty steps is not.

```
① RESOLVE     browser cache → OS cache → resolver → root → TLD → authoritative
              you now have an IP.                                    [DNS, UDP]

② CONNECT     ARP finds the gateway's MAC · packets routed hop by hop
              TCP three-way handshake to port 443.              [IP, TCP, L2]

③ SECURE      TLS handshake: server sends its certificate, browser verifies
              it against a CA, they agree a symmetric session key.      [TLS]

④ REQUEST     GET / HTTP/1.1 · Host: google.com
              server responds 200 OK + HTML.
              (may pass through a load balancer / CDN first.)          [HTTP]

⑤ RENDER      parse HTML → build DOM → fetch CSS, JS, images
              (each may need its own DNS + TCP + TLS) → paint.
```

**How to actually answer it:** give the five stages in ~45 seconds, then say *"I can go deeper on any of those."* **Do not** launch into a four-minute monologue — they want to see structure, then pick where to probe.

**The most common follow-ups, pre-answered:**

| They ask | You say |
|---|---|
| "Why port 443, not 80?" | HTTPS. Port 80 is plain HTTP. |
| "What if DNS is cached?" | Skip straight to stage ②. |
| "Where does the load balancer sit?" | Between stage ② and ④ — the IP you connected to is often the LB, not the server. |
| "What does TLS actually give you?" | Encryption, integrity, and server identity via the certificate. |
| "Why is a second visit faster?" | DNS cached, TCP connection possibly reused, browser cache for assets. |

**The Gotcha:** most candidates forget **ARP** in stage ② and **TLS** in stage ③ entirely. Including both is what makes the answer look complete rather than rehearsed off a blog.

**Recall:** *The five stages, in order, in one word each.*

> ✍️ **Blank page, 6 min.** Write all five stages with two details each. **Do this one properly** — it's the highest-value six minutes in CN.

## CN-07 · HTTP, status codes, HTTPS

**Anchor:** *"HTTP is stateless. Every request starts from nothing."*

**Methods:**
| Method | Does | Idempotent? |
|---|---|---|
| `GET` | read | ✅ |
| `POST` | create | ❌ |
| `PUT` | replace whole | ✅ |
| `PATCH` | partial update | ❌ |
| `DELETE` | remove | ✅ |

**Idempotent = doing it twice has the same effect as once.** `DELETE` twice → still deleted, so ✅. `POST` twice → two records, so ❌. This is asked directly and trips people up.

**Status codes — learn the families, then five specifics:**
```
1xx  informational
2xx  success            200 OK · 201 Created · 204 No Content
3xx  redirect           301 permanent · 302 temporary
4xx  YOUR fault         400 bad request · 401 unauthenticated
                        403 forbidden · 404 not found · 429 rate limited
5xx  SERVER's fault     500 internal error · 502 bad gateway · 503 unavailable
```

**401 vs 403** — the one they test: **401 = I don't know who you are** (log in). **403 = I know who you are, and no** (forbidden).

**HTTPS = HTTP + TLS.** What it gives you:
```
encryption  → nobody in between can read it
integrity   → nobody can modify it undetected
identity    → the certificate proves the server is who it claims
```
The TLS handshake uses **asymmetric** crypto to agree on a **symmetric** key, then uses the symmetric key for the actual data — because asymmetric is secure but slow, and symmetric is fast. Best of both.

**The Gotcha:** *"stateless"* means the server keeps no memory between requests. Cookies and tokens exist **precisely because** HTTP is stateless — that's the link to the next concept.

**Recall:** *401 vs 403? And what does "idempotent" mean?*

> ✍️ **Blank page, 4 min.** The five families with two codes each, plus the three things HTTPS gives you.

## CN-08 · REST, cookies, sessions, JWT

**Anchor:** *"Sessions remember on the server. Tokens remember on the client."*

**REST, in five rules:** stateless · resources as nouns in the URL (`/users/5`, not `/getUser?id=5`) · HTTP methods as the verbs · standard status codes · JSON.

**The three ways to stay logged in:**

```
COOKIE          a small string the browser stores and sends back
                automatically with every request to that domain.

SESSION         server keeps the real data; the cookie holds only a
                session ID.
                ┌────────┐  id=abc123   ┌──────────────────────┐
                │ browser│─────────────►│ server: abc123 = Riya│
                └────────┘              └──────────────────────┘
                ✅ revoke instantly   ❌ server must store state → scaling cost

JWT (token)     the client holds a signed token containing the data.
                Server verifies the signature — stores nothing.
                header.payload.signature
                ✅ stateless, scales across servers
                ❌ can't revoke before it expires
```

**The interview question:** *"Session vs JWT — which would you pick?"*
> *"Sessions if I need to revoke access immediately — a banking app. JWT if I have many servers and don't want shared session storage. The real trade-off is revocation versus statelessness."*

**The Gotcha:** a JWT is **signed, not encrypted.** Anyone can base64-decode the payload and read it. **Never put a password or anything secret in a JWT** — a genuinely important point and a great one to raise unprompted.

**Recall:** *Session vs JWT — what's the core trade-off?*

> ✍️ **Blank page, 3 min.** Draw both flows. Write one pro and one con each.

## 🔥 Rapid fire — 12 min. Notes CLOSED. Out loud.

1. Three DNS server levels, in order.
2. Which transport protocol does DNS use, and why?
3. What's an A record? A CNAME?
4. The five stages of typing google.com.
5. Where does ARP appear in that?
6. What does TLS give you — three things?
7. Which HTTP methods are idempotent?
8. 401 vs 403.
9. What's a 502?
10. Why is HTTP called stateless?
11. Session vs JWT — the core trade-off.
12. Is a JWT encrypted?

<details>
<summary>Answers</summary>

1. Root → TLD → authoritative.
2. UDP (port 53) — one small request/reply; a handshake would triple the cost.
3. A = name→IPv4. CNAME = alias to another name.
4. Resolve · Connect · Secure · Request · Render.
5. Stage ② — to find the MAC address of the default gateway.
6. Encryption, integrity, server identity via the certificate.
7. GET, PUT, DELETE. (Not POST or PATCH.)
8. 401 = not authenticated (who are you?). 403 = authenticated but not allowed.
9. Bad gateway — an upstream server gave an invalid response.
10. The server keeps no memory between requests; each one carries everything it needs.
11. Sessions can be revoked instantly but need server storage; JWTs are stateless but can't be revoked before expiry.
12. **No — signed, not encrypted.** Anyone can read the payload.
</details>
