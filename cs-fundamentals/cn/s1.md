## CN-01 · OSI vs TCP/IP

**Anchor:** *"Each layer talks only to the same layer on the other side."*

```
  OSI (7, theory)              TCP/IP (4, reality)      Example
  ┌──────────────┐             ┌──────────────┐
7 │ Application  │ ┐           │              │        HTTP, DNS, SMTP
6 │ Presentation │ ├──────────►│ Application  │        TLS, encryption
5 │ Session      │ ┘           │              │        sessions
  ├──────────────┤             ├──────────────┤
4 │ Transport    │ ──────────► │ Transport    │        TCP, UDP · PORTS
  ├──────────────┤             ├──────────────┤
3 │ Network      │ ──────────► │ Internet     │        IP, routers · IP ADDR
  ├──────────────┤             ├──────────────┤
2 │ Data Link    │ ┐           │              │        Ethernet, switches · MAC
1 │ Physical     │ ┴──────────►│ Network Access│       cables, signals
  └──────────────┘             └──────────────┘
```

**Mnemonic (bottom → top):** **P**lease **D**o **N**ot **T**hrow **S**ausage **P**izza **A**way.

**The three layers that matter for interviews — and their addresses:**
```
Layer 4  Transport  →  PORT      (which app on this machine?)
Layer 3  Network    →  IP        (which machine on the internet?)
Layer 2  Data Link  →  MAC       (which device on this local network?)
```

**Encapsulation** — each layer adds a header on the way down, strips it on the way up:
```
    [ data ]
   [TCP|data]              segment
  [IP|TCP|data]            packet
 [ETH|IP|TCP|data]         frame
```

**The Gotcha:** OSI is a **teaching model** — nothing actually implements 7 layers. Real networking is TCP/IP's 4. Say that; it shows you know the difference between the textbook and the world.

**Recall:** *Which layer owns ports, which owns IP, which owns MAC?*

## CN-02 · TCP vs UDP

**Anchor:** *"TCP is registered post. UDP is a postcard."*

```
TCP                                UDP
├─ connection first (handshake)    ├─ just send it
├─ guaranteed delivery             ├─ no guarantee
├─ in order                        ├─ any order
├─ resends lost data               ├─ lost is lost
├─ flow + congestion control       ├─ none
└─ 20-byte header, slower          └─ 8-byte header, fast
```

| | TCP | UDP |
|---|---|---|
| Connection | connection-oriented | connectionless |
| Reliability | guaranteed, ordered | best-effort |
| Speed | slower | **faster** |
| Header | 20 bytes | 8 bytes |
| Used by | HTTP, HTTPS, FTP, SMTP, SSH | DNS, DHCP, video calls, gaming, streaming |

**Why would anyone choose UDP?** Because **for live video, a late packet is worthless.** TCP would stop everything to resend a frame you've already scrolled past. UDP drops it and moves on — you'd rather have a moment of pixelation than a freeze.

**The Gotcha:** *"Which is better?"* has no answer, and the question is a trap for people who memorised "TCP = reliable = good." **Reliability costs latency.** State the trade-off and give the video-call example.

**🎤 Say it:** *"TCP guarantees delivery and order, which costs time. UDP has no guarantees but is fast — right for live video, where a resent frame arrives too late to be useful anyway."*

**Recall:** *Give one situation where UDP is genuinely the better choice, and why.*

## CN-03 · Three-way handshake & teardown

**Anchor:** *"Can you hear me? Yes, can you hear me? Yes."*

```
   CLIENT                                    SERVER
      │                                         │
      │────────  SYN  (seq = x)  ──────────────►│   "let's talk. my number is x"
      │                                         │
      │◄──── SYN-ACK (seq=y, ack=x+1) ─────────│   "ok. mine is y. got yours"
      │                                         │
      │────────  ACK (ack = y+1)  ─────────────►│   "got yours too"
      │                                         │
      │═════════ connection open ═══════════════│
```

**Why three, not two?** **Both sides must agree on sequence numbers.** Two messages would confirm only one direction — the server would never know the client received its number. Three is the minimum for mutual confirmation.

**Teardown takes four** — because closing is one direction at a time:
```
   FIN ──►        "I'm done sending"
   ◄── ACK        "noted"
   ◄── FIN        "I'm done too"     ← separate message: the server may still
   ACK ──►        "noted"              have had data left to send
```
That's **half-close**: one side can stop sending while still receiving. It's the reason teardown needs four steps and setup only needs three.

**The Gotcha:** *"Why 3 for open but 4 for close?"* — a favourite follow-up. Answer: **connection setup is symmetric, teardown isn't.** Each side closes independently, so the server's ACK and FIN can't be combined.

**Recall:** *Why three steps to open but four to close?*

## CN-04 · Flow control vs congestion control

**Anchor:** *"Flow control protects the receiver. Congestion control protects the network."*

```
FLOW CONTROL                      CONGESTION CONTROL
sender ──────► receiver           sender ───►[ network ]───► receiver
              (slow, small buffer)            (crowded)

"don't overwhelm ME"              "don't overwhelm the ROADS"
mechanism: receiver advertises    mechanism: sender infers loss and
           a WINDOW SIZE                     slows itself down
```

| | Flow control | Congestion control |
|---|---|---|
| Protects | the **receiver** | the **network** |
| Who decides | receiver (advertised window) | sender (infers from packet loss) |
| Mechanism | sliding window | slow start, AIMD |

**Congestion control, in brief:** start small, double each round trip (**slow start**), and on packet loss cut back hard, then grow slowly (**additive increase, multiplicative decrease**). TCP treats loss as a signal that the network is full.

**The Gotcha:** these two get conflated constantly, and the one-word separator is **who you're protecting** — the receiver vs the network. Lead with that and the rest follows.

**Recall:** *Flow control vs congestion control — who is each one protecting?*
