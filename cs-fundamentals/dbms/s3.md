## DB-09 · ACID

**Anchor:** *"All or nothing · rules never break · as if alone · survives a crash."*

```
   TRANSFER ₹500 from A to B

   A -= 500     ←── crash HERE ──→   money vanishes
   B += 500                          unless the whole thing is ATOMIC
```

| | Property | Means | Broken if |
|---|---|---|---|
| **A** | Atomicity | all steps, or none | money debited but never credited |
| **C** | Consistency | DB rules hold before and after | a balance goes negative when it can't |
| **I** | Isolation | concurrent txns don't see each other's half-work | you read a value someone later undid |
| **D** | Durability | committed = survives a crash | server dies, your commit is gone |

**How each is actually implemented** — say this and you're well past the definition:

```
Atomicity + Durability  →  the WRITE-AHEAD LOG
                           write the intent to the log FIRST, then the data.
                           crash → replay the log (redo) or reverse it (undo)

Isolation               →  locks, or MVCC (multi-version concurrency control)

Consistency             →  constraints, plus the other three doing their jobs
```

**The Gotcha:** **Consistency is the odd one out.** A, I and D are things the database *machinery* provides. C is largely *your* constraints being upheld — a lot of people can't say what C means because it's the vaguest. Being able to say that distinction is a strong signal.

**Recall:** *Which ACID property does the write-ahead log provide, and how?*

## DB-10 · Isolation levels & the three anomalies

**Anchor:** *"Three ways to be lied to. Pick which ones you'll tolerate."*

**Learn the anomalies first — the levels are just which ones you allow.**

```
DIRTY READ            you read a value another txn wrote but then ROLLED BACK.
                      You read something that never existed.

NON-REPEATABLE READ   you read a row twice in one txn and got different values.
                      Someone UPDATED it in between.

PHANTOM READ          you run the same query twice and get different NUMBERS of
                      rows. Someone INSERTED matching rows in between.
```

**The distinction that gets asked:** non-repeatable = *a row changed*. Phantom = *rows appeared*. Update vs insert.

| Level | Dirty | Non-repeatable | Phantom |
|---|---|---|---|
| **READ UNCOMMITTED** | ✅ can happen | ✅ | ✅ |
| **READ COMMITTED** | ❌ | ✅ | ✅ |
| **REPEATABLE READ** | ❌ | ❌ | ✅ |
| **SERIALIZABLE** | ❌ | ❌ | ❌ |

**How to remember it:** the table is a **staircase** — each level down blocks one more anomaly, in the order the anomalies are listed. Draw the staircase, not the words.

**The trade-off (always say this):** stricter isolation = more locking = **less concurrency and slower**. `SERIALIZABLE` is correct and slow; most real systems run `READ COMMITTED` (Postgres, Oracle default) or `REPEATABLE READ` (MySQL default).

**The Gotcha:** the highest level is not "best." Choosing `SERIALIZABLE` everywhere is a performance mistake, and saying *"I'd pick the weakest level that's still correct for this workload"* is the mature answer.

**Recall:** *Non-repeatable read vs phantom read — what's the difference?*

## DB-11 · Indexing

**Anchor:** *"A book's index — you don't read the whole book."*
**Yaad rakho:** *"Kitaab ka index — poori kitaab nahi padhni padti."*

```
WITHOUT INDEX                      WITH INDEX (B+ tree)
scan all 10 million rows                    [50]
O(n)                                     ╱      ╲
                                      [25]      [75]
                                     ╱   ╲     ╱   ╲
                                   ...   ...  ...  ...
                                   ▼
                              leaf nodes hold the actual pointers,
                              and are LINKED → range queries are fast
                              O(log n)
```

**Why B+ tree and not a hash index?** A hash gives O(1) for `=` but is **useless for ranges** (`BETWEEN`, `>`, `ORDER BY`). B+ trees keep leaves sorted and linked, so range scans are cheap. That's why they're the default.

| | Clustered | Non-clustered |
|---|---|---|
| What it is | the **table rows themselves** sorted by this key | a separate structure pointing at rows |
| How many | **one per table** (data can only be sorted one way) | many |
| Speed | faster — data is right there | extra hop to fetch the row |

**When an index HURTS — the question that separates people:**

```
every INSERT / UPDATE / DELETE must also update every index
  → writes get slower
  → indexes take storage
  → an index on a low-cardinality column (gender, is_active) is often
    useless: the DB will just scan the table anyway
```

**The Gotcha:** *"Should you index every column?"* — **no.** Index what you filter, join and sort on. Every index is a tax on every write. Reciting only the benefits is the giveaway that you've never actually built anything.

**Recall:** *Name two situations where adding an index makes things worse.*

## DB-12 · SQL vs NoSQL · CAP

**Anchor:** *"SQL for relationships. NoSQL for scale and shapeless data."*

| | SQL | NoSQL |
|---|---|---|
| Schema | fixed | flexible |
| Scaling | **vertical** (bigger machine) | **horizontal** (more machines) |
| Guarantees | ACID | often eventual consistency (BASE) |
| Joins | yes | usually not |
| Best for | banking, orders, anything relational | logs, catalogues, real-time feeds |

**Types of NoSQL, one line each:** key-value (Redis) · document (MongoDB) · column-family (Cassandra) · graph (Neo4j).

**CAP theorem — awareness level, but know the shape:**
```
        Consistency
            ╱╲          In a distributed system, when a network
           ╱  ╲         PARTITION happens, you must choose:
          ╱    ╲        consistency OR availability. You can't have both.
   Availability──Partition tolerance
                        P isn't optional — networks fail.
                        So the real choice is CP or AP.
```
- **CP** — refuse to answer rather than answer wrongly (banking).
- **AP** — always answer, may be slightly stale (social feeds).

**The Gotcha:** *"pick 2 of 3"* is the common but sloppy phrasing. **Partition tolerance isn't a choice** — networks fail whether you like it or not. The real decision is C or A *during* a partition. Saying that is a genuinely strong answer.

**Recall:** *Why is "pick any 2 of CAP" misleading?*
