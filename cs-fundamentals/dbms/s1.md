## DB-01 · Keys

**Anchor:** *"A key is a promise of uniqueness. A foreign key is a promise about someone else."*

```
STUDENT                                 COURSE
┌─────┬────────┬───────┬────────┐      ┌──────┬─────────┐
│ id  │ email  │ name  │course_id│─────►│ id   │ title   │
└─────┴────────┴───────┴────────┘      └──────┴─────────┘
  ▲       ▲                ▲              ▲
  │       │                └─ FOREIGN     └─ PRIMARY of COURSE
  │       └─ CANDIDATE (also unique)
  └─ PRIMARY (the chosen one)
```

| Key | Meaning |
|---|---|
| **Super key** | any set of columns that's unique (may have extras) |
| **Candidate key** | a *minimal* super key — remove any column and uniqueness breaks |
| **Primary key** | the candidate key you picked. Unique + **NOT NULL** |
| **Alternate key** | the candidate keys you didn't pick |
| **Foreign key** | points to another table's primary key. **Can be NULL** |
| **Composite key** | a primary key made of 2+ columns |

**The Gotcha:** a **primary key can never be NULL; a foreign key can.** (A NULL foreign key just means "not linked to anything yet.") This exact contrast is asked constantly.

**Referential integrity:** you cannot insert a `course_id` that doesn't exist in COURSE. Delete a course that students point to and the DB must do something: `CASCADE` (delete them too), `SET NULL`, or `RESTRICT` (refuse).

**Recall:** *Candidate key vs primary key vs super key — in one line each.*

## DB-02 · Normalization

**Anchor:** *"Store a fact once, point to it from everywhere else."*

**Why it exists — start here, not with the definitions.** This table is unnormalized:

```
┌────┬──────────┬───────────────┬──────────┬────────────┐
│ id │ student  │ courses       │ dept     │ dept_head  │
├────┼──────────┼───────────────┼──────────┼────────────┤
│ 1  │ Dhanashri│ DSA, DBMS     │ CSE      │ Dr. Rao    │
│ 2  │ Paritosh │ DBMS          │ CSE      │ Dr. Rao    │
└────┴──────────┴───────────────┴──────────┴────────────┘
```

**Three things break — these are "the anomalies":**

| Anomaly | The failure |
|---|---|
| **Update** | Dr. Rao is replaced → you must edit *every* CSE row. Miss one → contradictory data. |
| **Insert** | A new department with no students yet → you literally cannot record it. |
| **Delete** | Delete the last CSE student → the department vanishes too. |

**Now the forms. Each one fixes a specific problem:**

```
1NF   no repeating groups — every cell holds ONE value
      "DSA, DBMS" in one cell → split into two rows

2NF   1NF + no PARTIAL dependency
      (only matters when the key is COMPOSITE)
      key = (student_id, course_id), but student_name depends on
      student_id ALONE → move it out

3NF   2NF + no TRANSITIVE dependency
      student_id → dept → dept_head
      dept_head depends on the key only THROUGH dept → move it out

BCNF  3NF + every determinant is a candidate key
      (a rare edge case of 3NF; know the name and that it's stricter)
```

**Memory hook:**
```
1NF → one value per cell
2NF → whole key       (no part of the key decides anything)
3NF → nothing but the key   (no non-key column decides another)
```

> *"Every non-key attribute depends on the key, the whole key, and nothing but the key."* — memorise this sentence. It's 2NF and 3NF in nine words, and it's a very good thing to say out loud.

**The Gotcha:** **2NF only applies when the primary key is composite.** Single-column key → you're already in 2NF automatically. People miss this constantly.

**Recall:** *Name the three anomalies. Then: what does 3NF remove?*

## DB-03 · Denormalization

**Anchor:** *"Normalize for correctness. Denormalize for speed."*

```
NORMALIZED               → correct, no duplication, but a report
                           needs 5 JOINs and runs slowly

DENORMALIZED             → deliberately duplicate a column to skip
                           the join. Faster reads, riskier writes.
```

**When it's the right call:** read-heavy systems, analytics, dashboards. Storing `order.customer_name` alongside `customer_id` avoids a join on every single order listing.

**What it costs:** the data can now disagree with itself. You've traded a *guaranteed* correctness for speed, and you must maintain that consistency yourself.

**The Gotcha:** *"Is normalization always good?"* — **no**, and that's the answer they're fishing for. *"Normalize by default; denormalize deliberately when reads dominate and you can accept managing the duplication."* Nuance scores here.

**Recall:** *When would you deliberately denormalize?*

## DB-04 · Relationships & ER basics

**Anchor:** *"Many-to-many always needs a third table."*

```
ONE-TO-ONE      user ── profile
                → foreign key on either side

ONE-TO-MANY     department ──< employees
                → foreign key on the MANY side (employee.dept_id)

MANY-TO-MANY    students >──< courses
                → a JUNCTION table:
                  ENROLLMENT(student_id, course_id)
                  composite primary key of the two FKs
```

**The Gotcha:** you *cannot* represent many-to-many with foreign keys alone — there's nowhere to put them. The junction table isn't a design preference, it's a requirement. **This is asked as "how do you model students and courses?" in almost every DBMS round.**

**ER vocabulary, in 20 seconds:** entity = table · attribute = column · relationship = the link · cardinality = 1:1 / 1:N / M:N. Weak entity = can't exist alone (an `OrderLine` without an `Order`).

**Recall:** *How do you implement many-to-many, and why can't foreign keys do it alone?*

<details>
<summary>Answers</summary>

1. Super = any unique column set. Candidate = minimal super key. Primary = the candidate you chose.
2. Primary: **never**. Foreign: **yes** — means "not linked yet."
3. A primary key made of two or more columns.
4. `CASCADE` (delete children), `SET NULL`, or `RESTRICT` (refuse).
5. Update, insert, delete anomalies.
6. One value per cell — no repeating groups.
7. Only when the primary key is **composite**.
8. Transitive dependencies — a non-key column determining another non-key column.
9. *"Every non-key attribute depends on the key, the whole key, and nothing but the key."*
10. BCNF is stricter: every determinant must be a candidate key.
11. Read-heavy systems where joins are the bottleneck and you accept managing duplication.
12. A junction table with a composite key of both foreign keys — FKs alone can't express it.
</details>
