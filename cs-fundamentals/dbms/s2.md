## DB-05 · Joins

**Anchor:** *"INNER keeps matches. OUTER keeps orphans too."*

```
   A          B                 INNER          LEFT           FULL
 ┌───┐      ┌───┐              ┌───┐         ┌───┐          ┌───┐
 │ 1 │      │ 2 │              │   │         │▓▓▓│          │▓▓▓│
 │ 2 │      │ 3 │              │▓▓▓│  2,3    │▓▓▓│  1,2,3   │▓▓▓│  1,2,3,4
 │ 3 │      │ 4 │              │   │         │   │          │▓▓▓│
 └───┘      └───┘              └───┘         └───┘          └───┘
                             only matched   all of A +    everything,
                                            matches       NULLs to fill
```

| Join | Returns |
|---|---|
| `INNER` | rows matching in **both** |
| `LEFT` | **all of left** + matches; NULLs where none |
| `RIGHT` | all of right + matches |
| `FULL OUTER` | everything from both; NULLs on both sides |
| `CROSS` | every combination (Cartesian product) — `m × n` rows |
| `SELF` | a table joined to itself |

**The self-join — asked constantly:**
```sql
-- each employee with their manager's name (both live in EMPLOYEE)
SELECT e.name AS employee, m.name AS manager
FROM employee e
LEFT JOIN employee m ON e.manager_id = m.id;
```
**Use `LEFT`, not `INNER`** — the CEO has no manager, and `INNER` would silently drop them. That kind of detail is exactly what's being tested.

**The Gotcha:** *"Find rows in A that are NOT in B"* is a LEFT JOIN plus a NULL check:
```sql
SELECT a.* FROM a LEFT JOIN b ON a.id = b.a_id WHERE b.a_id IS NULL;
```

**Recall:** *You need employees who have no manager. Which join, and what's in the WHERE?*

## DB-06 · Query execution order

**Anchor:** *"SQL runs in a different order than you write it."*

```
YOU WRITE                    THE DATABASE RUNS
   SELECT                       1. FROM / JOIN     ← get the rows
   FROM                         2. WHERE           ← filter rows
   WHERE                        3. GROUP BY        ← make groups
   GROUP BY                     4. HAVING          ← filter groups
   HAVING                       5. SELECT          ← pick columns
   ORDER BY                     6. ORDER BY        ← sort
   LIMIT                        7. LIMIT           ← cut
```

**This single diagram answers three separate interview questions:**

**1. WHERE vs HAVING?** `WHERE` filters **rows before grouping**; `HAVING` filters **groups after**. Aggregates like `COUNT()` don't exist yet at WHERE-time.
```sql
WHERE  salary > 50000        -- ✅ a row-level fact
WHERE  COUNT(*) > 5          -- ❌ groups don't exist yet
HAVING COUNT(*) > 5          -- ✅
```

**2. Why can't I use a SELECT alias in WHERE?** Because `SELECT` runs *after* `WHERE`. The alias doesn't exist yet. (You *can* use it in `ORDER BY` — that runs after.)

**3. Why must every non-aggregated SELECT column be in GROUP BY?** Because the group has many rows, and the DB wouldn't know which one to show.

**The Gotcha:** `COUNT(*)` counts rows including NULLs. **`COUNT(column)` skips NULLs.** Different answers, and it's a favourite trick question.

**Recall:** *Why can't you use a SELECT alias in the WHERE clause?*

> ✍️ **Blank page, 3 min.** Write the 7-step execution order from memory. It's the highest-value thing in this session.

## DB-07 · Subqueries & window functions

**Anchor:** *"A subquery answers once. A correlated subquery answers per row."*

```sql
-- normal subquery: runs ONCE, independent
SELECT * FROM employee
WHERE salary > (SELECT AVG(salary) FROM employee);

-- correlated: runs once PER ROW, references the outer query
SELECT * FROM employee e
WHERE salary > (SELECT AVG(salary) FROM employee WHERE dept = e.dept);
                                                            ▲ the outer row
```
Correlated subqueries are **slow** — one execution per outer row. Say that; it shows you think about cost.

### Window functions — the modern way

```sql
SELECT name, dept, salary,
       RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS r
FROM employee;
```
Aggregate **without collapsing rows.** `PARTITION BY` = the grouping, `ORDER BY` = the ordering within each group.

```
name     dept  salary   ROW_NUMBER  RANK  DENSE_RANK
Riya     CSE   90000        1         1       1
Aman     CSE   90000        2         1       1      ← tie
Dhanashri CSE  80000        3         3       2
                                      ▲       ▲
                          RANK skips to 3   DENSE_RANK doesn't skip
```

**The Gotcha:** `ROW_NUMBER` is always unique. `RANK` gives ties the same number and **skips** the next. `DENSE_RANK` gives ties the same number and **doesn't skip**. This exact three-way distinction is asked directly.

**Recall:** *RANK vs DENSE_RANK vs ROW_NUMBER — what happens on a tie?*

## DB-08 · The 5 queries you must write cold

**Anchor:** *"Five queries. Everything else is a variation."*

**1. Nth highest salary** — the most-asked SQL question in existence.
```sql
SELECT DISTINCT salary FROM employee
ORDER BY salary DESC LIMIT 1 OFFSET 1;          -- 2nd highest

-- the version that impresses:
SELECT * FROM (
  SELECT name, salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r
  FROM employee
) t WHERE r = 2;
```
**Why `DENSE_RANK` and not `RANK`?** With two people on the top salary, `RANK` skips 2 entirely and you'd get nothing back. Say this — it's the follow-up.

**2. Find duplicates**
```sql
SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;
```

**3. Delete duplicates, keep one**
```sql
DELETE FROM users WHERE id NOT IN (
  SELECT MIN(id) FROM users GROUP BY email
);
```

**4. Employees earning more than their manager** (self-join)
```sql
SELECT e.name FROM employee e
JOIN employee m ON e.manager_id = m.id
WHERE e.salary > m.salary;
```

**5. Top earner per department** (window function)
```sql
SELECT * FROM (
  SELECT name, dept, salary,
         RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS r
  FROM employee
) t WHERE r = 1;
```

**The Gotcha:** `NOT IN` returns **nothing at all** if the subquery contains a single NULL. Use `NOT EXISTS` when NULLs are possible. This bug is subtle, real, and a great thing to mention unprompted.

**Recall:** *Write the 2nd-highest-salary query two ways.*

> ✍️ **Blank page, 8 min.** Write all five from memory. **Then check.** This is the highest-value eight minutes in the DBMS course.

## 🔥 Rapid fire — 12 min. Notes CLOSED. Out loud.

1. INNER vs LEFT JOIN.
2. Employees with no manager — which join, what WHERE?
3. What does CROSS JOIN return?
4. The 7-step execution order.
5. WHERE vs HAVING.
6. Why can't a SELECT alias be used in WHERE?
7. `COUNT(*)` vs `COUNT(column)`.
8. Normal vs correlated subquery — and which is slower?
9. RANK vs DENSE_RANK vs ROW_NUMBER on a tie.
10. What does PARTITION BY do?
11. 2nd highest salary — why DENSE_RANK over RANK?
12. Why can `NOT IN` return nothing unexpectedly?

<details>
<summary>Answers</summary>

1. INNER = only matches. LEFT = all left rows, NULLs where no match.
2. `LEFT JOIN` on manager, `WHERE m.id IS NULL`.
3. Every combination — `m × n` rows.
4. FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
5. WHERE filters rows before grouping; HAVING filters groups after.
6. SELECT runs after WHERE — the alias doesn't exist yet.
7. `COUNT(*)` counts all rows; `COUNT(col)` skips NULLs.
8. Normal runs once; correlated runs once per outer row — correlated is slower.
9. ROW_NUMBER: unique always. RANK: ties share, then **skips**. DENSE_RANK: ties share, **no skip**.
10. Splits rows into groups for the window function without collapsing them.
11. With tied top salaries RANK skips rank 2 entirely and returns nothing.
12. A single NULL in the subquery makes every comparison unknown. Use `NOT EXISTS`.
</details>
